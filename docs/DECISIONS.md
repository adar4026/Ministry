# DECISIONS — Ministry

Журнал архитектурных решений (Architecture Decision Records).

Каждое решение фиксируется здесь с обоснованием.
Это позволяет понять контекст через месяцы и годы, не восстанавливая его по переписке.

---

## ADR-001 — Платформа: Expo (React Native)

**Дата:** Июль 2026  
**Статус:** Принято

**Решение:** Использовать Expo (React Native), а не Flutter, PWA или нативную разработку.

**Обоснование:**
- Один кодовую базу покрывает iOS, Android и Web
- Expo Go позволяет тестировать на телефоне без сборки
- React Native совместим с уже созданным React-прототипом
- Алексей знаком с React-экосистемой
- Большое сообщество, хорошая документация

**Альтернативы, которые не выбрали:**
- Flutter — другой язык (Dart), нет преемственности с прототипом
- PWA — плохой UX на iOS, нет доступа к нативным API
- Swift/Kotlin — только одна платформа, высокий порог входа

## ADR-002 — Хранилище: AsyncStorage (локально)

**Дата:** Июль 2026  
**Статус:** Принято (временно)

**Решение:** Хранить все данные локально через AsyncStorage до интеграции с A-Lex Core.

**Обоснование:**
- Простота: нет сервера, нет авторизации, нет сетевых запросов
- Приватность: данные не покидают устройство
- Достаточно для одного пользователя на одном устройстве
- Легко мигрировать позже: AsyncStorage → A-Lex Core API

**Ограничения:**
- Нет синхронизации между устройствами
- Нет резервного копирования в облако
- Риск потери данных при удалении приложения

**Планируемая миграция:** После интеграции с A-Lex Core (см. ADR-003)

## ADR-003 — Будущий источник истины: A-Lex Core

**Дата:** Июль 2026  
**Статус:** Запланировано

**Решение:** После создания A-Lex Core — Ministry переключается на него как единый источник истины для всех данных.

**Обоснование:**
- A-Lex Core станет центральным хранилищем для всей личной экосистемы Алексея
- Единая точка синхронизации между Ministry, Finance, Health и другими приложениями
- Резервное копирование и синхронизация между устройствами
- AI-функции (анализ, отчёты, прогнозы) требуют централизованных данных

**Требование к текущей архитектуре:** Не закладывать зависимости, которые усложнят эту миграцию. StoreContext должен оставаться единственным местом, где происходит работа с данными.

## ADR-004 — Процесс разработки: только через TASK

**Дата:** Июль 2026  
**Статус:** Принято

**Решение:** Любое изменение в кодовой базе описывается в TASK_XXX.md до начала реализации.

**Обоснование:**
- Предотвращает хаотичную разработку "по настроению"
- Claude Code получает чёткие границы задачи
- Каждая задача имеет критерий завершения
- Прогресс отслеживается в PROGRESS.md

**Правило:** Нет TASK — нет кода.

## ADR-005 — Навигация: expo-router

**Дата:** Июль 2026  
**Статус:** Принято

**Решение:** Использовать expo-router (файловая маршрутизация), а не @react-navigation вручную.

**Обоснование:**
- Файловая структура сама является документацией
- Современный стандарт Expo-экосистемы
- Deep linking из коробки
- Меньше boilerplate кода

## ADR-006 — Стандарт документации: A-Lex Project Standard

**Дата:** Июль 2026  
**Статус:** Принято

**Решение:** Ministry следует единому стандарту документации для всех проектов экосистемы A-Lex.

**Структура стандарта:**
```
CLAUDE.md
docs/
├── README.md
├── PROJECT_CONSTITUTION.md
├── ARCHITECTURE.md
├── ROADMAP.md
├── STATUS.md
├── PROGRESS.md
├── DECISIONS.md
├── CHANGELOG.md
├── VISION.md
└── TASK_XXX.md
```

**Обоснование:** Единая структура позволяет Claude Code работать с любым проектом экосистемы без восстановления контекста. Меняется предметная область — подход остаётся одинаковым.

**Проекты, следующие этому стандарту:** ALSAVI, Ministry, Finance, Health, Real Estate.

## ADR-007 — Процесс: Architecture Review Checklist как обязательный gate перед релизом

**Дата:** Июль 2026
**Статус:** Принято

**Решение:** Ввести Architecture Review Checklist как обязательный этап
процесса разработки для каждого TASK, начиная с TASK_005. Checklist должен
быть успешно пройден до Deploy и до простановки Git Tag.

Обновлённый порядок разработки:

```
TASK
  ↓
Implementation
  ↓
Commit
  ↓
Architecture Review Checklist
  ↓
Required Fixes (если есть)
  ↓
Final Approval
  ↓
Deploy
  ↓
Git Tag
  ↓
Next TASK
```

**Обоснование:**
- Architecture Review Checklist проверяет **соответствие архитектуре**
  (architectural compliance), а не корректность реализации — это отдельная
  проверка, дополняющая, а не заменяющая обычную верификацию/тестирование.
- Deploy и Git Tag не должны происходить, пока checklist не пройден
  успешно — это обязательный quality gate перед каждым релизом.
- Впервые применяется к TASK_005 (см. `docs/TASKS/TASK_005A.md`, раздел
  "Architecture Review Checklist").
- Если во время реализации обнаруживается архитектурное ограничение или
  расхождение с утверждённой архитектурой — реализация останавливается,
  проблема документируется, вносится изменение в архитектурный документ
  (или создаётся новый ADR), и только после этого реализация продолжается.
  Никакие ad hoc архитектурные изменения "по ходу кодирования" не
  допускаются.

**Правило:** Ни один TASK не может быть задеплоен или помечен git tag без
успешного прохождения Architecture Review Checklist.
