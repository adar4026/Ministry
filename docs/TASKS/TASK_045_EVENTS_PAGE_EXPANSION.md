## 1. Заголовочный блок

Точный визуальный референс — заголовок страницы «Профиль» (TASK_044):
крупный тёмно-синий заголовок (`fontSize:28, fontWeight:700, color:
DS.navy`), светло-синий подзаголовок (`fontSize:14, color: DS.subText`),
те же боковые отступы (`paddingHorizontal:4` внутри `content{padding:16}`).
Заголовок — «События», подзаголовок — «Важные даты и мероприятия».
Находится внутри прокручиваемого содержимого (`ScrollView`), выше строки
поиска.

Порядок элементов на странице: заголовок/подзаголовок → действия
добавления → поиск → фильтры тем → карточки. «Добавить тему» не входит в
пронумerованный порядок владельца (только «действие добавления события»
названо явно) — размещена в одном ряду с «Добавить событие» сразу под
заголовком, как второе действие того же смыслового блока, а не как
отдельный шестой раздел страницы.

## 2. «Добавить событие» — переиспользование существующей формы

Кнопка на странице «События» переходит на существующий маршрут `/add`
(тот же экран, что открывается через центральный «+» в таб-баре) с
параметром `?focus=event` (`router.push`, тот же паттерн, что уже
использует `/entry?id=…`/`/entry?date=…` в `hours/history.tsx` и
`hours/month/[key].tsx`).

`app/(tabs)/add.tsx` читает `focus` через `useLocalSearchParams`. Экран
`/add` сейчас НЕ содержит промежуточного выбора типа записи — это плоский
`ScrollView` с тремя карточками (Часы / Событие / Речь) друг под другом.
Когда `focus === "event"`, рендерится только карточка события — это и есть
«сразу в режиме создания события, без промежуточного выбора»: пользователь
не видит и не должен прокручивать мимо карточек «Часы»/«Речь». Без
параметра (переход через таб-бар) поведение экрана не меняется — все три
карточки, как раньше.

Используется та же `EventForm`, тот же `saveEvent` (`StoreContext`) — вторая
независимая форма не создаётся. Так как `StoreContext` — единственный
источник состояния, сохранённое событие немедленно видно в общем списке,
фильтре «Все», своей теме и результатах поиска на странице «События» без
дополнительной логики синхронизации.

## 3. Пользовательские темы событий

### Модель данных (см. §5 ниже для полного обоснования)

Новый тип `CustomCategory { id: string; name: string }`
(`src/types/index.ts`). Новая коллекция в `StoreContext`/AsyncStorage:
`customCategories`, ключ `mj_custom_categories_v1`, по умолчанию `[]` —
тот же паттерн аддитивного ключа без миграции, что `mj_profile_v1`
(TASK_042).

`MinistryEvent.category` расширен с закрытого union `Category` до `string`
— значение остаётся либо системным ключом `Category` (`pioneer`,
`appointment`, …), либо `id` пользовательской темы. Существующие события
(с системными строковыми значениями) остаются валидными без миграции.

### Создание темы

Новая функция `addCustomCategory(name)` в `StoreContext`:
- обрезает пробелы по краям и схлопывает внутренние повторы пробелов;
- пустая строка/строка из пробелов → `{ ok: false, error: "empty" }`;
- регистронезависимое сравнение (после нормализации пробелов) против
  меток системных тем (`CAT[...].label`) И названий уже существующих
  пользовательских тем → дубликат отклоняется, `{ ok: false, error:
  "duplicate" }`;
- иначе создаёт `{ id: uid(), name }`, сохраняет через `usePersistentState`
  (переживает перезапуск приложения) и возвращает `{ ok: true, category }`.

UI: кнопка «＋ Добавить тему» на странице «События» (в одном ряду с «＋
Добавить событие») открывает существующий компонент `Modal`
(`src/components/Modal.tsx`, тот же, что уже используют модалки
редактирования события/речи на этой странице) с полем названия и парой
действий «Отмена»/«Сохранить». Инлайн-ошибка показывает причину отказа
(пустое имя / дубликат), поле не сбрасывается при ошибке.

### Отображение и переиспользование

Новая чистая функция `categoryMeta(categoryId, customCategories)`
(`src/data/constants.ts`) разрешает `categoryId` в `{label, bg, tx, dot}`:
сначала системный словарь `CAT`, затем пользовательская коллекция по
`id`, иначе — тот же запасной вариант `CAT.other`, что уже использовался
до этой задачи для любого нераспознанного значения. Пользовательские темы
получают единый, отдельный от всех системных цвет (cyan) — не путаются
визуально ни с одной существующей темой.

`Badge` и dashboard-`EventCard` получают новый необязательный проп
`customCategories` (по умолчанию `[]` — существующие вызовы без него не
меняют поведения); страница «События» и Home («Последние события») его
передают. `EventForm` получает обязательный проп `customCategories`;
список тем в его `ChipSelector` — системные темы + пользовательские,
показывается на создании И на редактировании (одна и та же форма).
Фильтр на странице «События» получает по одному чипу на каждую
пользовательскую тему, сразу после сохранения — без перезапуска экрана
(тот же реактивный `StoreContext`).

### Известное ограничение (осознанно вне рамок TASK_045)

Экспорт/импорт резервной копии (TASK_013, `src/data/backup.ts`) НЕ
расширен для пользовательских тем: `MinistryBackupData` не включает
`customCategories`, а `validateEvent()` по-прежнему принимает только
значения из `CATEGORY_KEYS` (системные темы) — сохранено намеренно
неизменным, чтобы не сломать существующий тест
`"rejects an event with an unsupported category"` и не расширять область
задачи на подсистему бэкапа. Следствие: если пользователь создаст события
с пользовательской темой, экспортирует резервную копию и попытается
импортировать её (в том числе на этом же устройстве после переустановки),
импорт такого события будет отклонён валидацией как «повреждённые данные»
— пользовательские темы сами по себе в бэкап не попадают вовсе. Сами
пользовательские темы (введённые с телефона) не теряются при обычной
работе приложения — только резервное копирование/восстановление их не
охватывает. Это зафиксированное ограничение, а не побочный дефект;
расширение формата бэкапа — предмет отдельной будущей задачи.

## 4. Точный срок в карточках событий

Новый чистый модуль `src/data/eventElapsed.ts`:
- `eventElapsed(iso, now)` — точная календарная разница (годы → месяцы →
  остаток дней, с учётом разной длины месяцев и високосных лет — не деление
  миллисекунд на фиксированные 30 дней), симметрично для прошлого И
  будущего;
- `formatEventElapsed(elapsed)` — рендерит `"Сегодня"` для сегодняшней
  даты, иначе `"прошло …"`/`"через …"` + части `N г./N мес./N дн.`
  (нулевые части опускаются).

Не переиспользует и не изменяет `src/data/dateFormat.ts`'s
`calendarElapsed()`/`formatElapsedRu()` — та пара сознательно
рассчитана только на прошлое (будущая дата целенаправленно схлопывается в
нули: `formatElapsedRu` возвращает `""`, `formatProfileEventElapsed`
возвращает `"менее 1 мес"`), и от этого поведения зависит существующий,
уже прошедший тест `dateFormat.test.ts` (`"future dates are handled safely
… формат: 'менее 1 мес'"` для `ProfileHeroCard`). Реализация будущей ветки
как реального симметричного расчёта (а не нулей) сломала бы этот тест —
поэтому для страницы «События» заведена независимая пара функций, а не
правка общей.

Старая `timeElapsed()` (`src/data/constants.ts`), округлявшая до целого
месяца, удалена — единственным вызывающим кодом была именно эта страница
(оба типа карточек — событие и речь).

## 5. Архитектурное решение по темам — обоснование

Изучены: модель `MinistryEvent`/`Category` (`src/types/index.ts`),
`CAT`/`CATEGORY_KEYS` (`src/data/constants.ts`), `StoreContext.tsx`,
`EventForm.tsx`, `Badge.tsx`, dashboard `EventCard.tsx`, `backup.ts`.

Выбранный вариант — минимально рискованный, полностью в рамках
существующей `StoreContext`/AsyncStorage архитектуры:
- системные темы остаются стабильными встроенными значениями (`CAT`,
  `CATEGORY_KEYS` не меняются);
- пользовательские темы — отдельная коллекция со своим устойчивым `id` и
  отображаемым `name` (`CustomCategory`), отдельный ключ хранения;
- событие ссылается на устойчивый `id` темы (строка) — не на текст;
  для системных тем это те же самые стабильные строковые ключи, что и
  раньше (`"pioneer"`, `"appointment"`, …);
- ни одно старое событие не требует ручной миграции — тип `category`
  расширен (не заменён), старые значения остаются валидными;
- состояние тем не дублируется — единственный источник:
  `StoreContext.customCategories`, читается через `useStore()` везде, где
  нужно (страница «События», `EventForm`, `Badge`/`EventCard`).

Переименование/удаление пользовательских тем — не реализовано (по прямому
указанию: «можно не включать, если потребуется заметно расширить объём
задачи»).

### Уточнение по ходу реализации — переполнение экрана длинной темой

При визуальной проверке на 320px длинное название пользовательской темы
(один чип шире экрана) не переносилось на новую строку — `flexWrap`
переносит между чипами, но не сжимает чип, который сам по себе шире
контейнера. Исправлено в общем `ChipSelector`
(`src/components/ui.tsx`) — единственном общем месте для всех трёх
потребителей (страница «События», `RecordForm`, `EventForm`): чип получил
`maxWidth: 200`, его текст — `numberOfLines={1}` (переполнение обрезается
многоточием). Существующие метки (месяцы, системные категории) короче
этого предела — видимых изменений для них нет.
