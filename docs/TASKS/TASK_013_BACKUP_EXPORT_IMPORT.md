# TASK_013 — Резервная копия данных: экспорт / импорт (Safari → PWA)

**Дата:** Июль 2026
**Статус:** В реализации (не задеплоено, не закоммичено)

---

## 1. Проблема

На iOS Safari и установленное на экран «Домой» PWA-приложение Ministry могут
использовать раздельные контейнеры локального хранилища. Пользователь имеет
реальные данные в Safari; свежеустановленный PWA стартует с пустым
хранилищем — секции Главной (`Текущий служебный год`, `Последние события`,
итоги часов) пусты в PWA.

Нужен безопасный ручной способ перенести данные: экспорт из Safari → файл →
импорт в PWA.

---

## 2. Затрагиваемые ключи хранилища (AsyncStorage)

| Ключ | Тип | В бэкап? | Обоснование |
|------|-----|----------|-------------|
| `mj_records_v1` | `HourRecord[]` (легаси месячные итоги) | Да | Активен, влияет на Главную/Часы |
| `mj_events_v1` | `MinistryEvent[]` | Да | Влияет на «Последние события» |
| `mj_talks_v1` | `Talk[]` | Да | Часть ленты «События» (публичные речи) |
| `mj_sessions_v1` | `Session[]` (гранулярное время, TASK_005A) | Да | Авторитетный источник Home-итогов/служебного года там, где есть сессии |
| `mj_timer_v1` | `TimerState` | **Нет** | Control-state для crash-recovery таймера (TASK_005C), не отчётная сущность, не входит в агрегацию (см. `docs/TASKS/TASK_005C.md` §4). Перенос состояния таймера между устройствами бессмысленен и может ошибочно триггернуть Recovery Screen на новом устройстве с чужим `startedAt`. |
| (настройки/предпочтения) | — | Нет данных | Секция «Настройки» на экране Профиль (`app/(tabs)/profile.tsx`) целиком состоит из `Alert`-заглушек («Появится позже») — persisted-состояния пока не существует. Формат бэкапа версионирован и расширяем: категория настроек может быть добавлена в будущей версии формата без breaking change. |

Все 4 экспортируемых ключа читаются и пишутся исключительно через
`StoreContext.tsx` (`KEYS` constant) — единая точка доступа к данным
(ADR-003). Экспорт использует данные из `useStore()` (уже гидратированные и
в памяти); импорт пишет напрямую в AsyncStorage по тем же ключам и
перезагружает приложение, чтобы `StoreContext` перегидратировался.

## 3. Формат бэкапа

```typescript
type MinistryBackup = {
  format: "ministry-backup";
  version: 1;
  createdAt: string;   // ISO-8601
  appVersion: string;  // "0.4.4" на момент TASK_013
  data: {
    records: HourRecord[];
    events: MinistryEvent[];
    talks: Talk[];
    sessions: Session[];
  };
  counts: {
    records: number;
    events: number;
    talks: number;
    sessions: number;
  };
};
```

Только данные, которыми владеет и которые понимает Ministry — не дамп всего
`localStorage`/`AsyncStorage`. Версионируется (`version: 1`) для будущего
расширения (например, добавление категории настроек) без breaking change.

Имя файла: `ministry-backup-YYYY-MM-DD-HHmm.json`.

## 4. Архитектура реализации

Новые файлы:

- `src/data/backup.ts` — чистые, платформо-независимые функции: типы формата,
  `buildBackup()`, `validateBackupJSON()` (валидация + JSON.parse),
  `formatBackupFilename()`. Полностью юнит-тестируемо без DOM/AsyncStorage.
- `src/data/backupImport.ts` — `performImport(backup)`: снимок текущих
  4 ключей (`AsyncStorage.multiGet`) → запись новых значений
  (`AsyncStorage.multiSet`) → проверка чтением → при любой ошибке —
  восстановление снимка (rollback). Не трогает `mj_timer_v1` и любые другие
  ключи. Бросает `BackupImportError` с русским сообщением без технических
  деталей.
- `src/data/backupFile.web.ts` / `src/data/backupFile.ts` — платформенный
  слой ввода-вывода файла:
  - `.web.ts` (используется в браузере/PWA — единственная реально
    задеплоенная платформа проекта на сегодня): `saveBackupFile()` через
    `Blob` + временную ссылку `<a download>` (открывает системный
    share/save flow браузера/iOS); `pickBackupFile()` через скрытый
    `<input type="file">` + `FileReader`; `reloadApp()` через
    `window.location.reload()`.
  - `.ts` (fallback для не-web платформ — нативная сборка проекта пока не
    выпускается, см. `docs/STATUS.md` «Что не работает»): функции
    отклоняются с понятным сообщением «недоступно на этой платформе» —
    без добавления новых нативных зависимостей (`expo-file-system`,
    `expo-sharing`, `expo-document-picker` и т.п. в проекте не установлены;
    добавлять их ради непроверенной на устройстве нативной сборки — вне
    объёма TASK_013). Metro автоматически выбирает `.web.ts` на вебе и
    падает обратно на `.ts` на native — изоляция чистая, без runtime
    `Platform.OS`-ветвлений внутри общего кода.
- `src/components/settings/BackupSection.tsx` — UI: кнопки «Экспортировать
  данные» / «Импортировать данные», модалка предпросмотра/подтверждения
  (переиспользует существующий `src/components/Modal.tsx` и
  `PrimaryButton`/`DangerButton` из `src/components/ui.tsx`), состояния
  загрузки, защита от двойного нажатия.

Изменённые файлы:

- `app/(tabs)/profile.tsx` — секция «Данные» лишается заглушек «Экспорт» /
  «Импорт» / «Резервная копия» / «Восстановление» (теперь реализовано по-
  настоящему), «Синхронизация» (soon, A-Lex Core) остаётся. Новая секция
  «Резервная копия данных» с пояснительным текстом и `BackupSection`.
- `src/store/StoreContext.tsx` — экспортируется существующая константа
  `KEYS` (переименована в `STORAGE_KEYS` при экспорте) как единый источник
  правды об именах ключей для `backupImport.ts` — без изменения формы или
  поведения стора.

## 5. Правила валидации импорта (см. также постановку задачи)

Выполняются полностью до любой записи:

1. JSON парсится; синтаксическая ошибка → отказ.
2. `format === "ministry-backup"` — иначе отказ («не похоже на резервную
   копию Ministry»).
3. `version` — целое число ≥ 1; версия новее поддерживаемой (`> 1`) →
   отказ с сообщением «создано более новой версией приложения».
4. `createdAt` — валидная ISO-дата.
5. `data` — объект с четырьмя массивами (`records`, `events`, `talks`,
   `sessions`); отсутствие любого — отказ.
6. Ограничение размера: разумный верхний предел на количество элементов на
   категорию и общий размер строки JSON — защита от abuse/повреждённых
   файлов.
7. Каждый элемент каждой категории проверяется по форме и типам полей
   (см. типы в `src/types/index.ts`); даты — валидируемы через `Date`;
   `category`/`source` — из допустимого перечисления.
8. Дублирующиеся `id` внутри категории → отказ (сломали бы приложение).

Все сообщения — на русском, без технических деталей/стектрейсов.

## 6. Атомарность и откат

`performImport()`:

1. Снимок текущих значений 4 ключей (`multiGet`).
2. Запись новых значений (`multiSet`).
3. Контрольное чтение и сравнение с ожидаемым.
4. При любой ошибке записи/проверки — восстановление снимка (`multiSet`
   для существовавших значений, `multiRemove` для ранее отсутствовавших
   ключей) и выброс ошибки. Никогда не очищает всё хранилище целиком —
   изменяются только 4 явно поддерживаемых ключа.
5. Успех репортится только после успешной проверки.

---

## 7. Приватность

- Вся обработка — локально на устройстве; сеть не используется.
- Содержимое бэкапа никогда не логируется в консоль.
- Тесты и документация используют только синтетические данные.

---

## 8. Объём (Scope)

**Входит:** формат бэкапа, экспорт, сохранение/расшаривание файла, выбор
файла, валидация, предпросмотр импорта, явное подтверждение замены,
атомарность/откат, релоад приложения после успеха, тесты, документация.

**Не входит:** облачная синхронизация, аккаунты, серверное хранилище,
iCloud, автоматический перенос Safari→PWA, merge/разрешение конфликтов,
шифрование бэкапа, редизайн несвязанных экранов, bump версии, тег, деплой.

## 9. Тесты (план)

`src/data/__tests__/backup.test.ts` — построение бэкапа, состав категорий,
метаданные/counts, валидация (валидный/невалидный JSON, неверный формат,
неподдерживаемая версия, битые записи, дубликаты id, пустой но валидный
бэкап, неразумно большой payload).

`src/data/__tests__/backupImport.test.ts` — успешный импорт заменяет 4
ключа и не трогает остальные (включая `mj_timer_v1`); откат при сбое
записи; откат при сбое верификации; отмена (preview без confirm) не пишет
ничего.

`src/components/settings/__tests__/BackupSection.test.tsx` — рендер,
доступность кнопок, предпросмотр показывает верные counts, отмена не
вызывает запись, подтверждение вызывает импорт и релоад.

## 11. Architecture Review Checklist (ADR-007)

Пройден перед деплоем и тегом, согласно обязательному gate из ADR-007.
Реализация и последующее hardening (строгая валидация дат, фолбэк отмены
файлового пикера Safari/iOS) прошли независимое ревью (Opus) дважды —
финальный вердикт: **APPROVED WITH NON-BLOCKING NOTES** (два
незначительных, не блокирующих релиз замечания зафиксированы ниже без
изменения объёма задачи).

- [x] **Нет нового бэкенда или внешнего сервиса.** Вся обработка экспорта/
      импорта происходит локально в браузере/PWA; сетевые вызовы не
      добавлялись (`src/data/backup.ts`, `backupImport.ts`, `backupFile*.ts`
      не содержат `fetch`/`XMLHttpRequest`/сетевых SDK).
- [x] **Нет новой облачной синхронизации.** Раздел «Синхронизация»
      (A-Lex Core, «Скоро») в `app/(tabs)/profile.tsx` не изменялся и
      остаётся заглушкой; TASK_013 не заменяет и не расширяет её.
- [x] **Нет аутентификации.** Экспорт/импорт не требует входа, токенов,
      паролей; ничего не отправляется и не запрашивается с сервера.
- [x] **Нет миграции схемы вне версионированного формата бэкапа.**
      `mj_records_v1`/`mj_events_v1`/`mj_talks_v1`/`mj_sessions_v1` —
      те же ключи и та же форма данных, что и раньше (см. ARCHITECTURE.md);
      формат бэкапа сам по себе версионирован (`version: 1`), но не меняет
      схему хранения приложения.
- [x] **Нет изменения существующей гидратации рантайм-хранилища.**
      `usePersistentState` (`src/hooks/useStorage.ts`) не изменялся;
      единственное изменение `StoreContext.tsx` — экспорт уже существующей
      константы `KEYS` как `STORAGE_KEYS` (тот же объект, без изменения
      поведения).
- [x] **Нет изменения поведения восстановления таймера.**
      `mj_timer_v1`, `src/hooks/useTimer.ts`, `src/data/timer.ts` —
      не затронуты; `mj_timer_v1` сознательно исключён из бэкапа/импорта
      (см. §2 выше) и подтверждён тестом
      `backupImport.test.ts` («leaves unrelated storage keys (including
      mj_timer_v1) untouched»).
- [x] **Версия не поднимается.** `package.json` остаётся `0.4.4`.
- [x] **Тег не создаётся.** Последний тег остаётся `v0.4.4`.
- [x] **Модель приватности — только локальная.** Экспорт/импорт данных не
      покидает устройство; ничего не отправляется на GitHub, в аналитику
      или на любой внешний сервис; содержимое бэкапа никогда не
      логируется в консоль (подтверждено `grep` по всем файлам модуля —
      см. отчёты о верификации).
- [x] **Ограничения отката задокументированы честно.** `performImport()`
      — это application-level snapshot-and-rollback, а не физическая
      атомарность `AsyncStorage.multiSet`/`multiRemove` — явно
      зафиксировано в комментарии `src/data/backupImport.ts` (шапка файла)
      после ревью, без преувеличения гарантий.
- [x] **Живая проверка на физическом iPhone остаётся обязательным
      post-deploy шагом.** Не выполнялась и не может быть выполнена в
      рамках этой задачи браузерными средствами — см. §12 (инструкции для
      владельца) в финальном отчёте о релизе.

**Незначительные замечания независимого ревью (не блокируют релиз, не
устраняются в этом релизе по решению владельца):**

1. Строгий валидатор ISO-datetime (`isStrictISODateTime`,
   `src/data/backup.ts`) допускает невозможный календарный день при
   корректной форме/таймзоне (например, `"2026-02-30T00:00:00Z"`,
   которую V8 нормализует в март). Поля, использующие этот валидатор
   (`startTime`/`endTime`/`createdAt`/`updatedAt`) — только метаданные,
   не участвующие ни в агрегации Home/Часов, ни в отображении (подтверждено
   `grep` по `src/data/stats.ts`, `src/data/constants.ts`, `app/`) —
   низкий риск, вне объёма текущего hardening.
2. Фолбэк отмены файлового пикера (`onFocus` в
   `src/data/backupFile.web.ts`) теоретически может сработать преждевременно
   при необычном десктопном сценарии (alt-tab обратно в браузер, пока
   системный диалог выбора файла ещё открыт). На реальном таргете задачи
   (iOS Safari / установленное PWA, модальный in-app пикер) это
   недостижимо; сценарий не приводит к потере данных — просто требует
   повторного нажатия «Импортировать данные».

**Итог:** оба замечания приняты как известные, не блокирующие ограничения;
расширение объёма задачи для их устранения не производится по решению
владельца.
