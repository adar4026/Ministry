## 1. Проблема

На `/hours/stats` в `MonthlyStatsCard.tsx` строка из трёх информационных
чипов не помещалась по ширине карточки на мобильных экранах. Соседняя
колонка с крупным значением часов (`hoursDone`, например «3 ч 10 м»)
чрезмерно сжималась и текст рендерился по одному символу на строку
(«3», «ч», «1», «0», «м» — каждый на своей строке).

## 2. Диагностика и корневая причина

Прочитан `MonthlyStatsCard.tsx` целиком; измерены реальные computed styles
в браузере (dev-сервер, react-native-web) для узла `hoursDone` Text и его
предков.

Структура (`mainRow` → `bigValue` | `chips` → 3× `chip`):

- `mainRow`: `flexDirection: "row"`, без `flexWrap` (по умолчанию —
  `nowrap`) — `bigValue` и `chips` навсегда обязаны делить одну строку,
  сколько бы места ни требовалось.
- `bigValue`: только `flex: 1` (→ `flexGrow:1, flexShrink:1,
  flexBasis:0%` в реальном CSS) — без `minWidth`. Автоматический
  CSS-минимум флекс-элемента с переносимым текстом (`min-width: auto`)
  равен ширине **самого длинного неразрывного токена**, а не всей фразы —
  для «3 ч 10 м» это пара символов, то есть почти 0. Ничто не мешало
  `bigValue` схлопнуться почти до нуля.
- `chips`: `flexDirection: "row", gap: 8, flexWrap: "wrap"` — но **без
  `flex`/`flexGrow`/`flexShrink`/`flexBasis`/`minWidth` на самом
  контейнере**. Собственный `flexWrap` относится только к тому, как её
  трём детям расположиться *внутри* уже выделенной ей ширины — но
  поскольку сама `chips` ничего не запрашивает и ничем не ограничена, она
  всегда требует свою полную «естественную» (`max-content`) ширину, не
  сжимаясь ни на пиксель по своей инициативе.
- `chip` (каждый из трёх): `flex: 1, minWidth: 80` — это ограничивает
  **отдельный чип**, но не саму `chips`-обёртку.

Поскольку `chips` не декларирует `flexShrink`/`flexBasis`, а `bigValue`
использует `flexBasis: 0%` (нулевая «стартовая» ширина, вся ширина только
через `flexGrow`), при нехватке места браузер сжимает именно `bigValue` —
это стандартное поведение алгоритма распределения flex-shrink, взвешенного
по `flexBasis × flexShrink`; у `bigValue` эта величина близка к нулю. Итог
— `bigValue` получал буквально `width: 0px` (подтверждено computed style),
и текст переносился посимвольно, потому что для переносимого текста браузер
корректно резолвит «минимальную» ширину как ширину отдельного слова/символа,
а не всей фразы.

**Корневая причина одной фразой:** ни `chips`, ни `bigValue` не имели
собственного защищённого минимума ширины и `mainRow` не мог перенести
`chips` на новую строку — оба конкурировали за одну и ту же строку без
возможности разойтись.

**Ответ на диагностический пункт 9 (общий ли компонент чипа виноват):**
нет — `chips`/`chip` определены только внутри `MonthlyStatsCard.tsx`
(`grep` подтвердил единственное вхождение паттерна `chips:` в кодовой
базе); `PaceCard`/`ProjectionCard`/`ServiceYearStatsCard` используют
собственные независимые локальные стили grid/chip, не связанные с этим
файлом — исправление не требуется и не вносится там.

## 3. Реализованное решение

Только `src/components/stats/MonthlyStatsCard.tsx`, блок `styles`:

```ts
mainRow: { flexDirection: "row", flexWrap: "wrap", justifyContent: "space-between", alignItems: "flex-start", gap: 12 },
bigValue: { flex: 1, minWidth: 190, flexShrink: 0 },
...
chips: { flexDirection: "row", flexGrow: 1, flexShrink: 1, flexBasis: 0, minWidth: 200, gap: 8, flexWrap: "wrap" },
```

- `mainRow` теперь `flexWrap: "wrap"` — если `bigValue` и `chips` вместе
  не помещаются, `chips` переносится на новую строку под `bigValue`
  целиком, а не сжимается на месте.
- `bigValue` получил `minWidth: 190` (измерено `canvas.measureText` для
  `"123 ч 59 м"` — самого широкого реалистичного значения — при
  `fontSize:36, fontWeight:700`: ~180px; 190 даёт запас) и `flexShrink: 0`
  — минимум становится жёстким полом, а не мягким предпочтением, которое
  алгоритм shrink всё равно мог бы переопределить.
- `chips` получил `flexGrow: 1, flexShrink: 1, flexBasis: 0, minWidth:
  200` — теперь у неё есть реальный размер для участия в распределении
  места в `mainRow` (раньше не было никакого), а `minWidth: 200`, не
  помещающийся рядом с защищённым `bigValue` на мобильных ширинах,
  надёжно провоцирует перенос. Собственный `flexWrap: "wrap"` внутри
  `chips` не менялся — три чипа по-прежнему располагаются по 2 в строку
  (3-й переносится) уже внутри выделенной `chips` ширины.

Ничего не завязано на конкретную ширину устройства — решение выражено
целиком через относительные flex-ограничения (`minWidth`/`flexBasis`/
`flexShrink`/`flexWrap`), поэтому одинаково корректно на 320/375/428px и
на более широких экранах (см. §6). Ни `fontSize`, ни `fontWeight`, ни
`letterSpacing` не менялись — типографическая шкала TASK_023 сохранена
полностью.

## 4. Почему решение устойчиво на разных ширинах

- На узких экранах (320–428px) `bigValue`(190) + gap(12) + `chips`(200) =
  402px обычно превышает доступную ширину `mainRow` (~260–390px) — `chips`
  переносится на отдельную строку под `bigValue`, где занимает всю ширину
  карточки и раскладывает свои чипы через собственный `flexWrap` (2 в
  строке на 320–375px, все 3 в строке на 428px при коротких значениях).
- На широких экранах (десктопный веб) `mainRow` может быть достаточно
  широкой, чтобы `bigValue`(190) + `chips`(200+) поместились рядом — в
  этом случае компактная горизонтальная композиция сохраняется
  автоматически, без отдельного кода для этого случая (просто следствие
  того, что `flexWrap` не сработал, ширины хватило).
- `bigValue` с `flexShrink: 0` гарантированно не сжимается ниже 190px ни
  при каких обстоятельствах — крупное значение часов никогда больше не
  может развалиться посимвольно.
