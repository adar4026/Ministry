## 4. Обнаруженные баги (оба подтверждены до исправления)

### 4.1 На web `onScrollEndDrag`/`onMomentumScrollEnd` никогда не вызываются

Прочитан `node_modules/react-native-web/src/exports/ScrollView/
ScrollViewBase.js`: пропсы `onScrollEndDrag`/`onMomentumScrollEnd`
объявлены в типах, принимаются как пропсы, но **ни разу не вызываются** в
теле компонента — внутренний settle-debounce (100мс) на web повторно
вызывает только `onScroll`. Значит `WheelPicker.handleScrollEnd` (и,
соответственно, `snapToIndex`) на web никогда не срабатывал сам по себе.

**Подтверждено живьём** (`localhost:8082/entry`, dev-сервер, `react-native-
web` 0.21.2, до исправления): программная прокрутка барабана «часы» к
строке 3 — строка визуально центрируется (`opacity` управляется отдельным,
всегда срабатывающим `onScroll` → `scrollOffset` state), но кнопка
«Добавить» остаётся неактивной — `onChange`/`snapToIndex` не сработали,
значение в state не изменилось. Именно тот класс проблемы, который описал
владелец: «строка по центру, но значение не зафиксировано».

**Исправление:** в `onScroll` на web (`Platform.OS === "web"`) планируется
debounce 130мс (с учётом внутреннего 100мс debounce самого RNW — 130 с
запасом), сбрасываемый на каждый новый тик; по истечении вызывает тот же
`handleScrollEnd`. Native (iOS/Android) получает реальные
`onScrollEndDrag`/`onMomentumScrollEnd` от платформы и не использует этот
таймер вовсе (`if (Platform.OS !== "web") return;`).

### 4.2 `onChange`-дедупликация зависела от пропа `value`, а не от ref

Пока писались тесты на п. 4.1, обнаружен смежный race: `snapToIndex`
пропускал повторный `onChange` только если `item.value === value` (проп
компонента). В сценарии «реальный settle-евент срабатывает первым, затем
web-debounce срабатывает на тот же индекс ~130мс спустя» — если React ещё
не успел прокинуть обновлённый `value` обратно в компонент (в
синтетическом тесте — гарантированно не успевает; в реальном приложении
успевает почти всегда за счёт батчинга React, но не гарантированно),
`onChange` вызывался бы дважды для одного и того же settle.

**Исправление:** `onChange` теперь стоит в одном `if` с haptic-логикой,
которая уже использовала `ref` (`lastHapticIndex`), а не проп — оба теперь
гарантированно срабатывают ровно один раз на изменение индекса, независимо
от таймингов рендера родителя.

## 6. Побочная находка: не в скоупе этой задачи

При живой проверке reopen-сценария через **hard reload** прямо на
`/entry?id=...` (не через обычную in-app навигацию) барабаны открылись на
0ч/0м вместо сохранённых 2ч15м. Это не баг wheel picker — это уже
задокументированное в `entryScreen.test.tsx` (комментарий у теста «switches
to edit mode») архитектурное ограничение: `SessionForm`'s `useState`
инициализируется один раз при mount, а при hard reload `StoreContext` может
ещё не успеть догрузиться из `AsyncStorage`/`localStorage` к этому моменту.
Через обычную in-app навигацию (тап по записи в Истории) — проверено
живьём, открывается корректно (2 часа / 15 минут, «Сохранить» активна).
Не исправлялось — вне запроса, требует отдельного решения (например,
не монтировать `EntryScreen` до `loaded` стора).

Отдельно обнаружено: `npx jest` уже падал на чистом `HEAD` (`74ab22b`, без
единого изменения) на одном тесте —
`app/__tests__/dashboard_import_rehydration.test.tsx` (дата-зависимый,
