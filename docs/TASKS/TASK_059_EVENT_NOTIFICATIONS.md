## Цель

Владелец должен вовремя получать системные уведомления о предстоящих
событиях (`MinistryEvent`), с понятной схемой по умолчанию и настройками
в приложении.

У `MinistryEvent` хранится только дата (`"YYYY-MM-DD"`), без времени,
поэтому схема напоминаний фиксированная:

| Тип | Когда | Заголовок | Тело |
|-----|-------|-----------|------|
| `dayBefore` | накануне, **19:00** локального времени | `Завтра событие` | `«{название}»` |
| `sameDay`   | в день события, **09:00** локального времени | `Сегодня событие` | `«{название}»` |

Оба типа включаются/выключаются независимо; сверху — главный
переключатель «Уведомления о событиях».

## §1. Платформа и выбранный механизм (ключевое архитектурное решение)

**Реальная среда исполнения Ministry на iPhone владельца — это НЕ нативная
сборка.** `npm run deploy` = `expo export --platform web && gh-pages -d dist`
(`package.json`), приложение живёт на GitHub Pages (`baseUrl: "/Ministry"`,
`app.json`) и установлено на экран «Домой» как PWA — вся история проверок в
`docs/STATUS.md` привязана к хэшам gh-pages-бандла, а не к сборкам
Expo Go / TestFlight (см. также TASK_013: «Известное ограничение web/PWA»).

Следствие: `expo-notifications` **не подходит** — его планировщик
(`scheduleNotificationAsync`) не имеет web-реализации и на web-бандле
Ministry не сделает ничего. Добавление зависимости, которая на
единственном реально отгружаемом таргете является no-op, нарушило бы
правило «не дублируй существующие решения» и увеличило бы бандл без
пользы.

**Выбранный механизм — штатный веб-стандарт: Service Worker +
Notifications API.** Именно он даёт настоящее *системное* уведомление в
Центре уведомлений iOS/Android, а не «фейковое уведомление внутри
интерфейса» (последнее задачей прямо запрещено).

Важно: на iOS **`new Notification(...)` не поддерживается вообще** —
единственный работающий путь это `ServiceWorkerRegistration.showNotification()`.
Поэтому service worker обязателен, а не «желателен».

Service worker (`public/ministry-notifications-sw.js`) **намеренно не
содержит обработчика `fetch`** — он не кэширует и не перехватывает
навигацию. Это исключает риск залипшего бандла (класс проблем, из-за
которого PWA-обновления ломаются), и SW отвечает ровно за одно:
хранение расписания и показ уведомлений.

### Что реально работает и где

| Сценарий | iOS 16.4+ (PWA на экране «Домой») | Android / Chrome | Safari-вкладка на iOS |
|---|---|---|---|
| Запрос разрешения | ✅ | ✅ | ❌ API `Notification` отсутствует |
| Тестовое уведомление («Проверить уведомление») | ✅ | ✅ | ❌ |
| Уведомление, когда приложение открыто | ✅ | ✅ | ❌ |
| Уведомление вскоре после сворачивания (пока SW жив) | ✅ пока система не выгрузила SW | ✅ | ❌ |
| Догоняющая доставка при следующем открытии приложения | ✅ | ✅ | ❌ |
| Доставка ровно в 19:00/09:00 при полностью закрытом приложении | ❌ **системное ограничение** | ⚠️ только если браузер выдал `periodicsync` | ❌ |

### Системные ограничения (зафиксировано явно)

1. **iOS не даёт веб-приложениям планировщик.** `TimestampTrigger` /
   `showTrigger` (Notification Triggers API) не реализован ни в одном
   браузере в проде — origin trial в Chrome закрыт, WebKit его не
   поддерживает. Единственный способ разбудить закрытое веб-приложение в
   заданный момент — **Web Push с сервера**, а у Ministry сервера нет по
   архитектуре (ADR-002: всё локально, данные не покидают устройство).
   Добавление push-сервера означало бы отправку названий личных событий
   владельца на сторонний сервер — прямо против ADR-002.
2. **Следствие:** если PWA полностью закрыта (не в фоне) в 09:00, iOS
   уведомление в 09:00 не покажет. Оно будет показано **при первом
   открытии приложения** (догоняющая доставка, §3, шаг 1) — уведомление
   не теряется, но может опоздать.
3. **Требуется установка на экран «Домой».** В обычной вкладке Safari на
   iOS объект `Notification` не существует; экран показывает это
   отдельным понятным блоком (§4).
4. **Android/Chrome** дополнительно пытается зарегистрировать
   `periodicSync` (тег `ministry-reminders`). Если браузер его выдаёт —
   появляется настоящая фоновая доставка при закрытом приложении;
   интервал определяет браузер (обычно не чаще ~12 ч), поэтому это
   рассматривается как бонус, а не как гарантия.
5. **Разрешение отзывается только системой.** Если пользователь нажал
   «Не разрешать», повторный `requestPermission()` браузером
   игнорируется — экран в этом случае объясняет, что включить надо в
   системных настройках (iOS: Настройки → Уведомления → Ministry).

Единственная более надёжная альтернатива — перевод проекта на нативную
сборку (EAS Build + `expo-notifications`). Это отдельная задача уровня
смены таргета релиза, вне рамок TASK_059; здесь реализован максимально
надёжный вариант, доступный на текущем таргете.

## §2. Чистая логика — `src/data/notifications.ts`

Ни одной платформенной зависимости; полностью юнит-тестируется.

- `NotificationSettings = { enabled, dayBefore, sameDay }`,
  `DEFAULT_NOTIFICATION_SETTINGS = { enabled: false, dayBefore: true, sameDay: true }`
  — по умолчанию **выключено целиком**: приложение не запрашивает
  системное разрешение, пока владелец сам не включит главный переключатель.
- `REMINDER_TIMES` — `dayBefore: 19:00`, `sameDay: 09:00`.
- `reminderFireAt(dateISO, kind): Date | null` — момент срабатывания в
  **локальной зоне устройства**: `new Date(y, m - 1, d + offset, hour, minute)`.
  Локальный конструктор `Date`, а не UTC-арифметика — поэтому переход на
  летнее/зимнее время не сдвигает 19:00/09:00, и `d - 1` корректно
  переходит через границы месяца и года. Несуществующие даты
  (`2026-02-31`) и мусорные строки → `null`.
- `reminderId(eventId, kind)` = `` `${eventId}::${kind}` `` — **детерминированный**
  идентификатор. Это структурная гарантия отсутствия дублей: одно событие
  × один тип = ровно один идентификатор, сколько бы раз ни пересчитывалось
  расписание.
- `planReminders(events, settings, now): ScheduledReminder[]` —
  единственный источник истины о том, что должно быть запланировано:
  - `settings.enabled === false` → `[]` (то же для каждого выключенного типа);
  - **строго будущие** напоминания: `fireAt.getTime() > now.getTime()`
    (прошедшее событие и прошедший слот сегодняшнего дня отфильтровываются);
  - дедупликация по `id` (защита от дублей `event.id` в хранилище);
  - сортировка по `fireAt`, затем по `id` — стабильный вывод.
- `diffReminders(current, next)` — `{ add, remove, unchanged }`. Изменение
  даты или названия меняет `fireAt`/`body`, и напоминание попадает
  одновременно в `remove` и в `add` — то есть «отменить старое, создать
  новое» это следствие диффа, а не отдельная ветка кода.

## §3. Канал доставки — `src/utils/localNotifications.ts` / `.web.ts`

Тот же паттерн платформенного разделения, что у `profilePhotoStorage.ts`
/ `.web.ts` и `backupFile.ts` / `.web.ts` (Metro подставляет `.web.ts` на
web, jest-expo резолвит нативный файл).

Нативный файл — честный no-op (`"unsupported"`), потому что нативной
сборки у проекта сейчас нет; он существует, чтобы бандл RN собирался и
чтобы тесты не зависели от браузерных API.

Web-реализация (`localNotifications.web.ts`):

- `getNotificationSupport()` → `{ supported }` либо причина:
  `"needs-standalone"` (iOS, не установлено на экран «Домой»),
  `"no-api"` (браузер без Notification/ServiceWorker);
- `getPermissionState()` / `requestNotificationPermission()`;
- `syncReminders(reminders)` — регистрирует SW (один раз, кэш промиса) и
  шлёт ему полный желаемый набор;
- `sendTestNotification(delaySeconds)` — реальное системное уведомление
  через SW;
- `clearAllReminders()`.

Service worker (`public/ministry-notifications-sw.js`), состояние в
IndexedDB (`ministry-notifications` / `state`), поэтому переживает
выгрузку SW и перезапуск приложения. Алгоритм на любое пробуждение
(message / periodicsync / сработавший таймер):

1. **Догоняющая доставка:** все сохранённые напоминания с
   `fireAt <= now`, ещё не отмеченные доставленными, показываются
   немедленно и помечаются `delivered`. Этот шаг идёт **до** сверки с
   новым набором — иначе напоминание, срок которого наступил при
   закрытом приложении, было бы молча выброшено (его уже нет в
   `planReminders`, тот отдаёт только будущее).
2. **Сверка:** сохранённый набор заменяется присланным; флаги
   `delivered` переносятся по совпадающим `id`. Удалённое событие,
   выключенный тип, выключенный главный переключатель — всё это просто
   отсутствие `id` во входящем наборе, и напоминание исчезает вместе с
   таймером.
3. **Пере-взвод таймеров** на ближайшие напоминания
   (`setTimeout`, окно 24 ч, чтобы не держать бессмысленно длинные таймеры).
4. `notificationclick` → фокус на уже открытой вкладке приложения либо
   открытие `/Ministry/`.

`tag` уведомления = `id` напоминания: даже если браузер получит команду
показа дважды, ОС схлопнет их в одно — второй уровень защиты от дублей
поверх детерминированных `id`.

## §4. Экран «Уведомления» — `app/notifications.tsx`

Маршрут корневого `Stack` (вне группы `(tabs)`), как `app/upcoming-events.tsx`
— нижняя навигация там не рендерится, ничего скрывать не нужно;
**нижняя центральная кнопка «Добавить» не затрагивается вообще.**

Дизайн — существующая система Ministry, без новых токенов: `HomeBackground`,
`DS`, `SummaryCard` (`padding: 0, overflow: "hidden"` для списков строк),
`SectionHeader`, `BackButton`, круглый icon-chip `DS.heroBg` + `DS.accent`,
`SafeAreaView edges={["top","left","right"]}` — один в один как на
`/upcoming-events`.

Содержимое:

1. Заголовок «Уведомления» + `BackButton` (fallback `/profile`).
2. Описание: приложение напомнит о приближающихся событиях.
3. Карточка «Напоминания»:
   - `BellIcon` «Уведомления о событиях» — главный переключатель;
   - `MoonIcon` «За день до события» — подпись «В 19:00»;
   - `SunIcon` «В день события» — подпись «В 09:00».
   Оба типа `disabled` (полупрозрачны) при выключенном главном.
4. Карточка «Проверка» — строка «Проверить уведомление» с подписью
   «Придёт через несколько секунд»; отправляет **настоящее системное**
   уведомление через 5 секунд.
5. Блок разрешения (только когда оно не выдано): понятное объяснение +
   кнопка. Три состояния:
   - `default` → «Разрешить уведомления» (вызывает системный запрос);
   - `denied` → инструкция открыть системные настройки (iOS:
     Настройки → Уведомления → Ministry);
   - `needs-standalone` → «Добавьте Ministry на экран «Домой»…».

Включение главного переключателя при `permission === "default"` сначала
запрашивает разрешение и включается **только** если оно выдано —
переключатель не может остаться «включённым» без реального разрешения.

Новые иконки `MoonIcon` / `SunIcon` добавлены в существующий
`src/components/icons.tsx` тем же стилем (`react-native-svg`,
`strokeWidth 1.8`, `IconProps`) — новых файлов иконок не заводится.

## §5. Хранение и оркестрация — `src/store/StoreContext.tsx`

Настройки: ключ `mj_notifications_v1`, тот же `usePersistentState`, что и
у всех остальных коллекций (гидратация из AsyncStorage, запись только
после неё). Поэтому настройки переживают перезапуск приложения.

Пересоздание расписания живёт **в одном месте** — в эффекте
`StoreProvider`, а не в экранах:

```
useEffect(() => { syncReminders(planReminders(events, notificationSettings, new Date())) },
         [loaded, events, notificationSettings])
```

Это соответствует ADR-003 («StoreContext должен оставаться единственным
местом, где происходит работа с данными») и автоматически, без единой
дополнительной ветки, покрывает все требования задачи:

| Требование | Как выполняется |
|---|---|
| создание события → запланировать | `saveEvent` меняет `events` → эффект |
| правка даты/названия → отменить старые, создать новые | `saveEvent` меняет `events` → дифф в SW |
| удаление события → **обязательно** отменить | `deleteEvent` меняет `events` → `id` исчезает из набора |
| смена глобальных настроек → пересоздать/отменить для всех будущих | `notificationSettings` в зависимостях |
| восстановление из резервной копии | `replaceAllData` меняет `events` → тот же эффект |
| перезапуск приложения | эффект отрабатывает при `loaded` |

Плюс `setInterval` раз в 60 с, пока приложение открыто: пересчитывает
план и пингует SW, чтобы напоминание сработало и в том случае, если
система успела выгрузить SW вместе с его `setTimeout`. Интервал
заводится **только** если платформа поддерживает уведомления
(`isNotificationSupported()`), поэтому на native и в jest он не создаётся
и не оставляет висящих таймеров.

## §9. Как проверить настоящее уведомление на iPhone

1. Открыть задеплоенный Ministry в Safari и **«Поделиться» → «На экран
   „Домой“»** (в обычной вкладке Safari iOS уведомления веб-приложениям
   не выдаёт вовсе).
2. Запустить Ministry **с иконки на экране «Домой»**.
3. Профиль → **Уведомления** → включить «Уведомления о событиях» → iOS
   покажет системный запрос → **«Разрешить»**.
4. Нажать **«Проверить уведомление»**, свернуть приложение (свайп вверх)
   и подождать ~5 секунд — придёт настоящий системный баннер Ministry.
5. Боевая проверка: создать событие на **завтра** и убедиться, что
   напоминание «Завтра событие» приходит сегодня в 19:00 (приложение при
   этом должно быть открыто или в фоне — см. ограничение §1.2), либо что
   оно приходит при первом открытии приложения после 19:00.
