# TASK_019 — Home: ограничение «Ближайших событий» до 3 + отдельный экран полного списка

**Статус:** В РАБОТЕ.
**Основание:** ADR-004 (нет TASK — нет кода). Запрошено владельцем напрямую.

---

## 1. Проблема

Секция «Ближайшие события» на Главной уже ограничена тремя элементами
(`UpcomingEventsCard`, `LIMIT = 3`), но кнопка «Показать все →» вела на
вкладку «События» (`/timeline`) — общий таймлайн (прошлое + будущее,
события + речи, поиск/фильтры/редактирование), а не на выделенный список
именно предстоящих событий. Отдельного экрана с полным списком предстоящих
событий не было.

## 2. Ожидаемое поведение пользователя

- Главная показывает не более 3 ближайших предстоящих элементов
  (события + публичные речи, как и сейчас).
- Кнопка «Показать все →» открывает **новый выделенный экран**
  «Ближайшие события» со всем списком предстоящих элементов — не
  переключает на вкладку «События».
- Вкладка «События» (`/timeline`) не меняется и продолжает работать как
  раньше (полный таймлайн, поиск, фильтры, редактирование).
- Новый экран открывается сверху (root `Stack`, вне `Tabs`) — без нижнего
  таб-бара, со стандартной кнопкой «Назад», возвращающей на Главную.

## 3. Маршрут / навигация

- Новый файл: `app/upcoming-events.tsx` — **вне** группы `(tabs)`, на одном
  уровне с `app/service.tsx`. Регистрируется в корневом `Stack`
  (`app/_layout.tsx`, `headerShown: false` уже задан глобально) — поэтому
  экран не получает системный header и не входит в `Tabs`, значит нижний
  таб-бар (`TabBar`, рендерится только внутри `Tabs`) на нём не
  показывается автоматически — ничего вручную скрывать не нужно.
- Причина выбора: единственный существующий прецедент вложенного экрана
  без таб-бара (`app/(tabs)/hours/month/[key].tsx`) живёт внутри
  собственного `Stack` вкладки «Часы» (`app/(tabs)/hours/_layout.tsx`).
  Чтобы применить тот же приём к вкладке «Главная», пришлось бы превратить
  `app/(tabs)/index.tsx` в папку с собственным `_layout.tsx` (по аналогии с
  `hours/`) — это более широкая структурная правка навигационного дерева,
  которой требование п.14 явно просит избежать («не переструктурировать
  всё дерево навигации»). Корневой `Stack` уже используется для отдельных
  экранов вне вкладок (`service.tsx`) — это существующий, минимальный,
  архитектурно согласованный путь.
- Переход: `router.push("/upcoming-events")` из `UpcomingEventsCard`
  (вместо `router.push("/timeline")`).
- Кнопка «Назад» на новом экране: `router.canGoBack() ? router.back() :
  router.replace("/")` — второй вариант подстраховывает прямую загрузку/
  refresh страницы в вебе, когда истории навигации ещё нет.
- Существующие маршруты и вкладки не меняются.

## 4. Определение «предстоящего события»

Используется уже существующая семантика проекта (та же, что и в текущей
`upcomingItems()`): событие/речь **предстоящие**, если `date >= today`
(сравнение ISO-строк `"YYYY-MM-DD"`, где `today` — локальная календарная
дата устройства). Событие сегодняшним днём **включается** — так уже было
устроено до TASK_019, поведение не меняется.

Данные в проекте — **только календарная дата**, без времени
(`MinistryEvent.date` / `Talk.date`: `"YYYY-MM-DD"`), поэтому сортировка по
полному `date/time` не требуется. Сравнение ISO-строк вида `YYYY-MM-DD`
лексикографически эквивалентно хронологическому сравнению — доп.
парсинг в `Date` для самой сортировки не нужен (риска сдвига часового
пояса нет, так как строки не парсятся как `Date` для этой цели).

Для одинаковых дат порядок детерминирован явным вторичным ключом — `id`
(а не polагание на стабильность `Array.prototype.sort`, хотя она и
гарантирована спецификацией ES2019+/используемым Hermes).

## 5. Общий селектор

Расширена (не продублирована) существующая функция
`upcomingItems(events, talks, now, limit?)` в `src/data/constants.ts` —
она уже была единственным местом фильтрации+сортировки будущих
событий+речей для Главной. Изменение: параметр `limit` стал
**необязательным** — при `undefined` возвращается весь отсортированный
список без обрезки; вторичная сортировка по `id` добавлена для
детерминизма при совпадающих датах.

- `UpcomingEventsCard` (Главная): `upcomingItems(events, talks, now, 3)`.
- `app/upcoming-events.tsx` (новый экран): `upcomingItems(events, talks, now)`
  — без лимита, без произвольного окна в месяцах/годах.

Строковый рендер строки (заголовок + дата + «через N дней») вынесен в
`src/components/dashboard/UpcomingEventRow.tsx`, чтобы не дублировать
JSX/стили между `UpcomingEventsCard` и новым экраном.

## 6. Лимит Главной = 3

`UpcomingEventsCard` вызывает `upcomingItems(events, talks, now, 3)` —
как и раньше (было `LIMIT = 3`), поведение не изменилось, только источник
строки переиспользует `UpcomingEventRow`.

## 7. Полный список без лимита

`app/upcoming-events.tsx` вызывает `upcomingItems(events, talks, now)` —
без четвёртого аргумента, весь предстоящий список, без фильтра по
месяцам/годам. Список не копируется в отдельное состояние — читается
напрямую из `useStore()` при каждом рендере, поэтому после добавления/
редактирования/удаления события экран всегда показывает актуальные данные
(единый источник истины — `StoreContext`, без stale-копий).

## 8. Пустое состояние

Тот же текст, что и в `UpcomingEventsCard`: «Нет предстоящих событий» —
переиспользуется тот же паттерн (не придумывается новый визуальный стиль
пустого состояния).

## 9. Видимость «Показать все»

Правило: кнопка показывается, если есть **хотя бы одно** предстоящее
событие (т.е. когда список для Главной непустой — а он непустой тогда и
только тогда, когда общий список непустой, так как лимит 3 не может
превратить непустой список в пустой). Если предстоящих событий нет вовсе —
кнопка скрывается (раньше кнопка была видна всегда, даже при пустом
списке — это единственное поведенческое изменение в `UpcomingEventsCard`
за пределами самого маршрута кнопки).

## 10. Взаимодействие с карточкой события

На Главной строки «Ближайших событий» и раньше не были нажимаемыми (простой
`View`, без `onPress`, без перехода к «деталям события» — такого экрана в
проекте не существует). TASK_019 не добавляет новый flow «детали события»
ни на Главной, ни на новом экране — строки остаются информационными,
как и раньше (п.8 задания: «если flow не существует — не изобретать»).
Существующее поведение вкладки «События» (тап по элементу открывает
модалку редактирования `EventForm`/`TalkForm`) не меняется и не
переносится на новый экран — эти два экрана осознанно не идентичны по
поведению.

## 10a. Побочная находка: коллизия id SVG-градиента `HomeBackground`

При визуальной проверке нового экрана (запущенного из уже смонтированной
Главной, т.е. когда root `Stack` держит оба экрана в DOM одновременно —
обычное поведение стека для анимации/возврата назад) фон `HomeBackground`
на новом экране не отображался: рендерился плоский `DS.homeBase`, без
sage-градиента. Причина — `HomeBackground` использовал захардкоженный
`id="homeBg"` для `<LinearGradient>`; при двух одновременно смонтированных
экземплярах (Главная под новым экраном) в DOM оказывались два элемента с
одинаковым id, и `fill="url(#homeBg)"` второго экземпляра резолвился в
чужой (невидимый/нулевого размера) градиент. Исправлено:
`src/components/dashboard/HomeBackground.tsx` теперь генерирует
уникальный id через `useId()` (React 19) на каждый экземпляр. Это
существующий компонент, используемый Главной с TASK_010 — баг был скрытым,
пока `HomeBackground` не начал монтироваться в двух экземплярах
одновременно (впервые происходит именно из-за нового экрана TASK_019).
Исправление минимально и не меняет визуальный результат Главной (там и
раньше был единственный экземпляр).

## 11. Область изменений

- `src/data/constants.ts` — `upcomingItems()`: необязательный `limit`,
  детерминированный вторичный порядок по `id`.
- `src/components/dashboard/UpcomingEventRow.tsx` (новый) — общая строка
  предстоящего элемента.
- `src/components/dashboard/index.ts` — экспорт `UpcomingEventRow`.
- `src/components/UpcomingEventsCard.tsx` — использует `UpcomingEventRow`;
  кнопка «Показать все» ведёт на `/upcoming-events`; скрывается при пустом
  списке.
- `app/upcoming-events.tsx` (новый) — экран полного списка.
- `src/components/dashboard/HomeBackground.tsx` — уникальный id градиента
  через `useId()` (см. §10a).

## 12. Вне области (не трогаем)

- `app/(tabs)/timeline.tsx` (вкладка «События») и её поведение.
- Модель данных `MinistryEvent`/`Talk`, `StoreContext`.
- Другие карточки/секции Главной.
- Экраны Часы/Профиль/Добавить.
- Навигационное дерево `(tabs)/_layout.tsx` (список вкладок не меняется).

## 13. Тесты и критерии приёмки

- `src/data/__tests__/constants.test.ts` (дополнено): `upcomingItems()` —
  прошлые исключены, сегодняшние включены, будущие включены, сортировка от
  ближайшей к дальней, неотсортированный вход даёт отсортированный выход,
  >3 события → лимит 3 обрезает / без лимита возвращает все, <3 события
  обрабатываются корректно, одинаковые даты — детерминированный порядок,
  ISO-парсинг дат без сдвига на день (нет `Date`-парсинга для сравнения —
  тест фиксирует само отсутствие сдвига), пустой вход → пустой результат.
- Компонентные тесты: Главная показывает не более 3 элементов; «Показать
  все» не ведёт на `/timeline`; новый экран рендерит полный список и
  пустое состояние.

Реализация помечается «не закоммичено, не запушено, не задеплоено» —
ждёт решения владельца.
