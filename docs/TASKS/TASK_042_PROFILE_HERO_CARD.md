# TASK_042 — Интерактивная главная карточка профиля

## Контекст

Продолжение работы после TASK_041 (редизайн страницы «События»). Текущая
страница «Профиль» (`app/(tabs)/profile.tsx`) начинается с статичного блока:
аватар-плейсхолдер, жёстко закодированное имя «Пользователь» и четыре
жёстко заданных факта («Крещён», «Пионер с», «Стаж», «G-8»), все со
значением «—» — ни одно из этих полей не подключено к хранилищу и не
редактируется пользователем.

## Цель

Заменить этот статичный блок на первую, интерактивную карточку профиля:
необязательные фото + имя, и от 0 до 4 **пользовательских** памятных
событий (свободное название + дата, без системно закреплённых типов
«Крещение»/«Пионер»). Пользователь сам решает, какие события ему нужны.

Только верхняя карточка и её редактор. Остальные секции страницы
(«Настройки», «Данные», «Резервная копия данных», «О приложении»), фон
страницы, нижняя навигация и остальные экраны — не трогаются (это
TASK_043 и далее).

## Модель данных

Новые типы в `src/types/index.ts`:

```ts
export type ProfileEvent = {
  id: string;
  title: string;
  date: string; // ISO "YYYY-MM-DD"
};

export type UserProfile = {
  displayName?: string;
  profilePhotoUri?: string;
  events: ProfileEvent[]; // максимум 4, порядок массива = порядок отображения
};
```

Никаких `baptismDate`/`isPioneer`/`pioneerStartDate`. Хранится через
`usePersistentState` в `StoreContext` под новым ключом `mj_profile_v1`,
тем же способом, что и остальные коллекции — не отдельный storage-слой.
Seed — пустой профиль (`{ events: [] }`), определённый локально в
`StoreContext.tsx` (тот же паттерн, что уже применён к `SEED_SESSIONS`
в TASK_005A — не через `src/data/seed.js`, чтобы не трогать
задокументированный в CLAUDE.md privacy-контракт этого файла).

## Расчёт срока

Переиспользуется уже существующий чистый helper `calendarElapsed()`
(`src/data/dateFormat.ts`, TASK_018/025) — он уже считает полные
календарные годы/месяцы корректно (без UTC-сдвига, с учётом високосных
лет и конца месяца) и уже выставляет `isFuture`. Новый форматтер
`formatProfileEventElapsed()` берёт из него только `years`/`months`
(без `days` — в карточке профиля дни не показываются per ТЗ) и рендерит
компактный вид без точек («2 г 1 мес», не «2 года 1 месяц»), с
`"менее 1 мес"` при нулевых годах и месяцах. Существующий
`formatElapsedRu()` (с точками и днями) не трогается — используется
Главной как раньше.

## Фотография

В проекте не было ни одной зависимости для выбора изображений. Добавлена
`expo-image-picker` (`npx expo install`, официальный Expo SDK-модуль,
работает в Expo Go без пересборки) — согласовано с владельцем отдельным
вопросом перед реализацией. Web использует ту же технику, что уже
доказала себя в `src/data/backupFile.web.ts` (скрытый переиспользуемый
`<input type=file>`), но читает файл как data URI
(`FileReader.readAsDataURL`) вместо текста.

## Лимит в 4 события

Проверяется и в UI (кнопка «+ Добавить событие» скрывается на 4/4), и в
данных (`saveProfile` в `StoreContext` отбрасывает события сверх 4-го).

## Ограничения TASK_042

Не трогаем: остальные секции `/profile`, фон страницы, нижнюю навигацию,
Главную, Историю, Статистику, «События». Без авторизации, аккаунтов,
облачной синхронизации, серверной загрузки фото. Без специальных типов
«Крещение»/«Пионер». Commit/push/deploy — только по отдельному разрешению
владельца после проверки.

## Ревизия — финальные уточнения владельца

После первой реализации владелец уточнил три пункта, потребовавших
точечной переработки уже сделанного (не полной переделки):

**1. Лимит событий — 3, не 4.** `MAX_PROFILE_EVENTS` в `StoreContext.tsx`
изменён с 4 на 3. Профиль, уже сохранённый в незакоммиченной версии с
четырьмя событиями, безопасно нормализуется до первых трёх при загрузке
(`useEffect` в `StoreProvider`, один раз после гидратации) — без ручной
миграции пользователем.

**2. Горизонтальная раскладка вместо вертикальной.** `ProfileHeroCard`
переработан: имя — крупный центральный элемент под фото (не строка рядом с
ним), события — не список, а до 3 равных колонок в одну строку слева
направо. Незаполненные колонки (1-2 события) остаются визуально пустыми
без рамки/прочерка. Название колонки — маленький uppercase (только
`textTransform`, само значение не мутируется), дата и срок — крупнее и
контрастнее. Заголовок каждой колонки занимает фиксированную высоту
(2 строки) — дата и срок у всех колонок всегда начинаются на одном
уровне независимо от длины названия. На 320px дата/срок ужаты по
`fontSize` (адаптивно только внутри блока событий, не весь интерфейс) плюс
`adjustsFontSizeToFit` как native-only подстраховка.

**3. Редактор — по образцу A-Lex Finance.** `ProfileEditSheet` переписан на
нижнюю модальную плашку (`RNModal`, `animationType="slide"`,
`justify-content: flex-end`), а не центральный диалог: белая поверхность,
скругление только сверху (26px), затемнённый фон (`rgba(0,0,0,0.55)`),
крупный заголовок «Профиль» слева + круглая светло-серая кнопка закрытия
справа, `useSafeAreaInsets()` для нижнего отступа. Строки действий (фото,
события) — общий локальный компонент `ActionRow` (белая рамка, скругление,
серый chevron справа), визуально повторяющий `.prof-row` из A-Lex Finance
(изучено вживую через уже задеплоенный `https://adar4026.github.io/finance/`
— профиль оттуда взят только как визуальный референс, ничего оттуда не
скопировано напрямую и строка «Уведомления» не воспроизводится).

**4. Постоянное хранение фото на native.** Добавлена вторая зависимость —
`expo-file-system` (после проверки — в проекте её не было). Новый
`src/utils/profilePhotoStorage.ts` копирует выбранное фото из временного
кэш-URI `expo-image-picker` в постоянную директорию приложения
(`Paths.document/profile-photos/`, SDK 54 синхронный API `File`/`Directory`)
и удаляет старую копию — но только если она принадлежит этой директории
(никогда не удаляет исходное фото из галереи или внешний URI). Копирование
происходит не сразу при выборе в редакторе (это всё ещё черновик,
который можно отменить), а в момент нажатия «Готово» — иначе отмена
редактирования удалила бы уже подключённый файл. Ошибка копирования не
затрагивает старое фото (проверено тестом) и показывает inline-сообщение,
не закрывая редактор. Web не меняется — data URI остаётся
самодостаточной строкой, `profilePhotoStorage.web.ts` — pass-through.

Известное ограничение web/PWA: фото хранится как data URI прямо в
`AsyncStorage`/`localStorage` — крупные фото увеличивают размер профиля в
разы (base64 накладывает ~33% сверху к размеру файла), а `localStorage` в
большинстве браузеров ограничен ~5–10 МБ на origin; для очень больших фото
это единственное известное ограничение текущей web-архитектуры (нет
отдельного файлового хранилища в браузере в рамках этой задачи).
