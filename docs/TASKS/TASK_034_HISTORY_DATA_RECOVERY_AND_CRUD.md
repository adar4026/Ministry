# TASK_034 — Восстановление полной истории, открытие и удаление записей

**Дата:** Июль 2026
**Статус:** В работе

## 1. Запрос владельца

После TASK_033 на production обнаружены три связанные проблемы:

1. Клик по строке записи в списке под календарём не открывает запись.
2. Удаление записи из формы редактирования не удаляет её (либо запись
   снова отображается после возврата).
3. История показывает только новые записи `Session`; ~467 ч за 2025–2026
   (10 месяцев legacy `HourRecord`) не отображаются ни в одном режиме
   периода.

Полный текст задания — в сообщении владельца этой сессии (не дублируется
здесь построчно). Требование: не рисовать данные заново и не создавать
тестовые записи — вернуть уже существующим `HourRecord` видимость в новой
«Истории» и исправить реальный CRUD.

## 3. Изученная архитектура и первопричины

### 3.1 Почему пропала история (пункт 3)

`app/(tabs)/hours/history.tsx` (TASK_032/033) вычисляет календарь, список
и карточку «Итого» через `dailyMinutesForMonth`/`sessionsForMonth`/
`totalMinutesForPeriod` (`src/data/stats.ts`) — все три читают только
`sessions`, `records` (legacy `HourRecord`) в этот экран не передаётся
вообще. Для TASK_032 это было осознанным и корректным решением: экран
показывал только **текущий** календарный месяц, а
`legacyEntryBlockReason()` безусловно блокирует создание legacy-записи
для текущего месяца — то есть текущий месяц физически не может иметь
`HourRecord`. TASK_033 добавила навигацию по произвольным
месяцам/годам/«Всё время», но не обновила источник данных — поэтому
любой прошлый legacy-месяц (у владельца — все 10 из 2025–2026) показывает
пустую историю. Это подтверждено и в собственной прод-проверке
TASK_033 в `docs/STATUS.md`: «реальные данные владельца — 0 записей
`Session`, поэтому «История» на реальных данных пуста по всем трём
периодам — ожидаемо».

`monthTotal()` (`src/data/stats.ts`) уже реализует правильное
Session-first правило (§7 `TASK_005_ARCHITECTURE.md`) и уже используется
в `app/(tabs)/hours/month/[key].tsx` и `serviceYearAggregation()`
(`src/data/constants.ts`) — тот же примитив переиспользуется здесь, не
дублируется.

### 3.2 Почему строки списка не кликабельны (пункт 1)

`src/components/hours/HistorySessionRow.tsx` — обычный `View`, без
`Pressable`, без `onPress`. Это не регрессия: TASK_033 §6 прямо исключила
это из объёма («Редактирование записи по клику на строку списка… не
реализуется в этом заходе»), реализован был только клик по дню календаря
(`onDayPress` → `HistoryCalendar`). Требуемая функциональность просто ещё
не была написана.

### 3.3 Почему удаление не работает (пункт 2)

`app/entry.tsx`, `app/(tabs)/hours/month/[key].tsx` — оба вызывают
`Alert.alert(title, message, [{ text: "Отмена" }, { text: "Удалить",
onPress: () => deleteSession(id) }])`. `deleteSession`/`StoreContext`/
`usePersistentState` сами по себе корректны (проверено чтением кода —
`setSessions(ss => ss.filter(x => x.id !== id))`, запись в
`mj_sessions_v1` происходит в эффекте, гейтированном `loaded`, без гонки).

Первопричина — на уровень ниже: `node_modules/react-native-web/dist/
exports/Alert/index.js` реализует `Alert.alert()` как **полный no-op**
(`class Alert { static alert() {} }`) — на web-платформе диалог
подтверждения не появляется вообще, поэтому его деструктивный `onPress`
(который единственный вызывает `deleteSession`/`deleteRecord`) никогда не
срабатывает. Это не гипотеза — тот же факт уже задокументирован в
комментарии `src/components/settings/BackupSection.tsx:118-124` для
другого флоу (импорт бэкапа), где эта же особенность `react-native-web`
уже вызывала предыдущий продакшн-баг. Проект деплоится как web-бандл
(GitHub Pages, `npm run deploy`) — это и есть платформа, на которой
владелец наблюдает баг. На native (`Alert.alert` — реальный нативный
диалог) тот же код уже работал бы корректно.

### 3.4 Существующий legacy-редактор (пункт 4 задания владельца)

`app/(tabs)/hours/month/[key].tsx` **уже существует и не удалён** —
git-археология не понадобилась. Экран уже умеет:
- показывать legacy-итог месяца с подписью-объяснением, когда `Session`
  для месяца нет;
- открывать `RecordForm`-в-`Modal` для редактирования/удаления
  `HourRecord` (`saveRecord`/`deleteRecord`, уже с `Alert.alert`-подтверждением
  — подвержено той же web-проблеме §3.3);
- показывать/редактировать/удалять `Session` месяца по нажатию/долгому
  нажатию.

Маршрут живой и уже используется из `/hours/stats` и `HoursHeroCard.tsx`
(Главная). Решение — не создавать второй редактор, а провести туда
переход из «Истории» для legacy-месяцев (§4.4 ниже), как и предписывает
задание владельца («предпочтительно восстановить совместимый маршрут…
не создавать новую модель данных»).

### 3.5 Хаотичные записи (пункт 9 задания)

`grep` по трекаемому дереву (`app`, `src`) не нашёл ни одного места, где
код сам генерирует ID вида `prodverify*`/`test*`/`session-*` — `uid()`
(`src/data/constants.ts`) — единственный генератор ID для `Session`, без
префиксов; `saveSession()` в `app/entry.tsx` защищён от повторной отправки
(`submittedRef`, блокирует повторный тап до ре-рендера кнопки). Второго
маршрута `/entry`, конфликтующего с текущим, не найдено (`app/entry.tsx` —
единственный, `app/(tabs)/hours/entry.tsx` не существует, перенесён ещё в
TASK_030 follow-up). Правдоподобное объяснение «хаотичных» записей —
именно баг §3.3: если владелец пытался удалить пробную/ошибочную запись
через диалог подтверждения на web, ничего не происходило, и запись
оставалась. Прямая проверка `mj_sessions_v1` реального устройства
владельца в рамках этой задачи не производилась (заявленный подход задания
— read-only inspection в изолированном браузерном профиле, если
потребуется) — записи не удалялись эвристически.

## 4. Решения

1. **`totalMinutesForPeriod`** (`src/data/stats.ts`) — сигнатура
   расширена: принимает `records: HourRecord[]` наравне с `sessions`, и
   для всех трёх периодов (`month`/`year`/`all`) суммирует через
   `monthTotal()` (Session-first), а не только `sessions`. `all` собирает
   объединение месяцев из `records` ∪ `sessions` (тот же приём объединения
   ключей, что уже использует `serviceYearAggregation()`, но не
   переиспользует её код напрямую — там группировка по служебному году,
   здесь плоская сумма по календарным месяцам). Единственный
   вызывающий — `history.tsx`; сигнатура не была нигде более
   заморожена в Architecture Review, расширение безопасно.
2. **Календарь и список месяца** остаются Session-only по данным (как и
   раньше) — `dailyMinutesForMonth`/`sessionsForMonth` не меняются: у
   legacy-месяца достоверной подневной разбивки нет, придумывать её
   запрещено заданием. Вместо списка сессий для legacy-месяца
   (`monthSessions.length === 0` и в `records` есть запись за
   `viewYear`/`viewMonthIndex0+1`) `history.tsx` показывает:
   - подпись «Сохранён месячный итог без разбивки по дням»;
   - один кликабельный `LegacyMonthRow` с суммой часов месяца, ведущий на
     уже существующий `/hours/month/${year}-${MM}`.
   Если ни `Session`, ни `HourRecord` за месяц нет — прежнее «Нет записей
   за этот месяц».
3. **`HistorySessionRow`** становится `Pressable` (`onPress` проп,
   `accessibilityRole="button"`, `accessibilityLabel`, pressed-state той
   же формы, что уже использует day-picker в `history.tsx`).
   `history.tsx` передаёт `onPress={() => openSession(session.id)}` —
   переиспользует уже существующую `openSession()` (ранее вызывалась
   только из модала выбора дня с несколькими записями), второй обработчик
   не заводится. Открывает `/entry?id=<session.id>` — тот же маршрут, что
   и клик по дню календаря; определение записи всегда по `session.id`, не
   по дате/длительности.
4. **Кросс-платформенное подтверждение удаления** — новый
   `src/utils/confirm.ts`, `confirmAsync(title, message): Promise<boolean>`.
   Native — тонкая обёртка над `Alert.alert` (реальный диалог, как и
   сейчас). Web (`Platform.OS === "web"`) — `window.confirm(...)`
   (единственный синхронный, реально работающий в браузере механизм
   подтверждения без внешних зависимостей). Заменяет `Alert.alert(...,
   [Отмена, Удалить])` в `app/entry.tsx` (удаление `Session`) и
   `app/(tabs)/hours/month/[key].tsx` (удаление `HourRecord` и long-press
   удаление `Session`) — единственные два места в объёме этой задачи
   (History-CRUD). Остальные `Alert.alert`-подтверждения в проекте (Главная,
   `/timeline`, таймер) подвержены той же проблеме, но лежат вне рамок
   TASK_034 — отмечены отдельно, не трогаются здесь (см. §6).
5. **Возврат к legacy после удаления последней `Session` месяца** — не
   требует отдельного кода: `monthTotal()`/Session-first уже реализует это
   как чистую функцию правила (§7 `TASK_005_ARCHITECTURE.md`) — как только
   `sessions` для месяца становится пустым множеством, следующий рендер
   `history.tsx` (читающего `useStore().sessions` реактивно) автоматически
   переключает месяц на `legacyRecord`, если он есть. Проверяется тестом,
   не отдельной веткой кода.
6. **Годы/навигация** — `PeriodNav`/`handlePrev`/`handleNext` уже не
   ограничивают год снизу (просто `y ± 1`) — достаточно для доступа к
   самому раннему году с legacy-данными, отдельного кода не требуется.
