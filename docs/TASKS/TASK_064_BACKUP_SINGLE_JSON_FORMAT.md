# TASK_064 — Один формат резервной копии: JSON

**Дата:** Август 2026
**Статус:** Реализовано (не задеплоено, тег не проставлен)
**Предшественники:** TASK_013 (`docs/TASKS/TASK_013_BACKUP_EXPORT_IMPORT.md`),
TASK_062 (`docs/TASKS/TASK_062_BACKUP_V2_AND_RESTORE.md`)

---

## 1. Состояние до задачи

Раздел «Данные и резервные копии» содержал **три** действия:

| Строка | Файл | MIME |
|--------|------|------|
| Экспорт данных | `ministry-export-YYYY-MM-DD-HHmm.json` (с отступами) | `application/json` |
| Создать резервную копию | `ministry-backup-YYYY-MM-DD-HHmm.mfb` (компактный) | `application/octet-stream` |
| Восстановить из копии | — | — |

Оба файла несли **одну и ту же** полезную нагрузку формата v2
(`format: "ministry-backup"`, `version: 2`, `appVersion`, `createdAt`,
`counts`, `data` из шести коллекций, SHA-256 `checksum`). Различались
только имя, расширение и форматирование. Проверка (`validateBackupJSON`),
предпросмотр и восстановление (`performImport`: снимок → страховочная
копия → запись → сверка байтов и счётчиков → применение к `StoreContext`
→ откат при ошибке) уже работали и уже были поэлементными: каждая ошибка
называет сущность, номер, id, поле и причину.

Два изъяна, которые эта задача устраняет.

1. **Дублирование.** «Экспорт данных» и «Создать резервную копию»
   выгружали одно и то же. Владельцу приходилось решать, какой из двух
   одинаковых файлов — «настоящая» копия.
2. **Расширение `.mfb`.** Целостности оно не добавляло — контрольная
   сумма лежит внутри полезной нагрузки, а не в имени файла. Зато на
   iPhone `.mfb` не имеет зарегистрированного UTI: «Файлы» и iCloud Drive
   показывают его как неизвестный документ с вопросительным знаком. Копия,
   которой владелец не доверяет с виду, — плохая копия.

---

## 2. Решение

Один формат копии — **JSON**. CSV, Excel и PDF в эту задачу не входят
(CSV может пригодиться отдельно для отчёта по часам в Excel — это другая
задача).

### 2.1 Экран «Данные и резервные копии»

Две строки вместо трёх:

| Строка | Иконка | Подпись | Действие |
|--------|--------|---------|----------|
| Создать резервную копию | `ShieldIcon` | «Полная копия всех данных приложения» | Пишет `ministry-backup-YYYY-MM-DD-HHmm.json` |
| Восстановить из копии | `RotateCcwIcon`, `tone="danger"` | «Заменит все текущие данные приложения» | Предпросмотр → подтверждение → замена |

Под блоком — «Последняя копия: ДД-ММ-ГГГГ ЧЧ:ММ» либо «Резервная копия
ещё не создавалась» (`mj_last_backup_v1`, обновляется только созданием
файла). Строка «Экспорт данных» и функция `formatExportFilename()`
удалены. Блок «Синхронизация — скоро через A-Lex Core» не тронут;
облачной синхронизации не добавлялось.

### 2.2 Файл

| | Значение |
|---|---|
| Имя | `ministry-backup-YYYY-MM-DD-HHmm.json` |
| MIME | `application/json` |
| Форматирование | С отступами (2 пробела) — файл читаемый |

Тип и расширение теперь согласованы, поэтому Safari/iOS не дописывает к
имени лишнее расширение и сохраняет файл как известный документ.
Отступы контрольной сумме не мешают: она считается по **каноническому
JSON** разобранного объекта (сортировка ключей, без пробелов —
`src/data/sha256.ts`), а не по байтам файла.

### 2.3 Содержимое (формат v2, без изменений)

```typescript
type MinistryBackup = {
  format:     "ministry-backup";
  version:    2;
  appVersion: string;      // "0.4.4"
  createdAt:  string;      // ISO-8601
  counts: {
    records: number; events: number; talks: number;
    sessions: number; customCategories: number;
  };
  data: {
    records:  HourRecord[];
    events:   MinistryEvent[];
    talks:    Talk[];
    sessions: Session[];
    customCategories?: CustomCategory[];  // TASK_045
    profile?:          UserProfile;       // TASK_042
  };
  checksum: string;        // SHA-256 всего перечисленного выше, hex
};
```

Контрольная сумма считается по копии **без поля `checksum`** — иначе её
нельзя было бы вычислить — и проверяется при восстановлении до разбора
содержимого, чтобы изменённый файл назывался изменённым, а не «сломанной
записью». Это проверка целостности, а не защита: сумма без ключа.

**Новое в TASK_064:** объявленные в файле `counts` теперь сверяются с
фактическим содержимым. У копии v2 расхождение — критическая ошибка
(«Файл повреждён: в разделе «речи» указано 5, а фактически содержится
1.»); у копии v1 — примечание в предпросмотре, а не отказ: TASK_013 свои
счётчики никогда не проверял, и терять из-за них данные, которые файл
явно содержит, нельзя.

## 3. Совместимость со старыми копиями

Формат определяется **по содержимому файла, а не по расширению** — имя
файла в проверку не попадает вообще.

| Что открываем | Как распознаётся | Результат |
|---------------|------------------|-----------|
| Новый `.json` (v2) | `format` + `version: 2` + checksum | Восстанавливается, сумма «Проверена» |
| Старый `.mfb` (TASK_062, v2) | То же самое — внутри тот же JSON | Восстанавливается, сумма «Проверена» |
| Старый `.json` (TASK_013, v1) | `version: 1`, checksum отсутствует | Мигрируется; отсутствие суммы — не повреждение |

Новые копии создаются **только** как `.json`. `.mfb` больше не пишется,
но остаётся в списке `accept` файлового выбора
(`.json,.mfb,application/json,application/octet-stream`): у `.mfb` нет
зарегистрированного UTI, поэтому без `application/octet-stream` iOS
показывал бы уже созданные копии серыми и недоступными для выбора.
Константа `LEGACY_MFB_FILE_EXTENSION` документирует именно этот статус.

Восстановление копии v1 не затирает темы событий и профиль: в v1 их
попросту нет, поэтому соответствующие ключи на устройстве остаются
нетронутыми, и предпросмотр говорит об этом отдельной строкой.

## 4. Что не блокирует восстановление

Разделение ошибок на критичные и совместимые — из TASK_062, сохранено и
покрыто тестами.

**Критичные** (восстановление невозможно): неверный JSON; файл не
является копией Ministry; отсутствие обязательного `id`; отсутствие или
неверный формат обязательной даты; неверная checksum у v2; расхождение
`counts` у v2; недопустимые `year`/`month`/`hours`/`durationMinutes`/
`source`; дубликат `id`; текстовое поле неверного типа.

**Совместимые** (принимаются как есть):

| Случай | Поведение |
|--------|-----------|
| `talk.number: null` | Нормальное «без номера». Не блокирует и не заменяется на `75` |
| `talk.number` отсутствует | Нормализуется в `null`, отмечается в примечаниях |
| `talk.number: "75"` | Ошибка — намерение владельца не угадывается |
| `record.creditHours` (TASK_039) | Сохраняется дословно |
| `event.category` = id пользовательской темы (TASK_045) | Принимается |
| Отсутствующий `note`/`title`/`location` | Нормализуется в `""` |
| Неизвестные лишние поля | Сохраняются: элемент копируется целиком |
| Устаревшие `counts` у v1 | Примечание, не отказ |

Ни одна запись не удаляется молча ради успешного импорта: копия
восстанавливается целиком либо не восстанавливается вовсе. Значения
личных текстовых полей (`note`, `title`, `location`) в сообщения об
ошибках не попадают — только структурные поля (даты, числа, id).

## 5. Безопасное восстановление (без изменений)

`performImport()` (`src/data/backupImport.ts`):

1. Снимок текущих значений всех поддерживаемых ключей.
2. Страховочная копия текущих данных в `mj_backup_safety_v1`; без неё
   восстановление не начинается.
3. Запись через штатные ключи приложения — только тех коллекций, которые
   копия реально содержит.
4. Контрольное чтение: побайтовое сравнение **и** сверка фактических
   счётчиков с `counts` из копии.
5. `replaceAllData()` — применение к живому `StoreContext` последним
   шагом той же транзакции.
6. При любой ошибке — откат снимка; если не удался и откат, сообщение
   честно об этом говорит.

Это application-level snapshot-and-rollback, а не физическая атомарность
`AsyncStorage.multiSet` — формулировка не преувеличена. `mj_timer_v1` и
любые другие ключи не затрагиваются.

Предпросмотр до замены показывает: статус проверки, дату создания, версию
копии, версию приложения, состояние контрольной суммы, таблицу «Категория
/ Сейчас / В копии» по записям часов, сессиям, событиям и речам (плюс
темы событий, если копия их содержит), примечания миграции и
предупреждение о замене. Кнопка «Восстановить» есть только у пригодной
копии; при ошибке — только «Закрыть».

## 9. Объём (Scope)

**Входит:** единый формат `.json`, удаление дублирующего экспорта, две
строки на экране, отметка последней копии, сверка объявленных счётчиков,
чтение старых `.json` (v1) и `.mfb` (v2), распознавание формата по
содержимому, тесты, документация.

**Не входит:** CSV/Excel/PDF (в том числе отчёт по часам для Excel —
отдельная будущая задача), облачная синхронизация (блок A-Lex Core не
тронут), аккаунты, шифрование копий, merge/разрешение конфликтов, bump
версии приложения, тег, деплой.
