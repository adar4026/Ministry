**Дата:** Август 2026
**Статус:** Реализовано (не задеплоено, тег не проставлен)

## 1. Проблема

Владелец не смог восстановить свою же резервную копию от 22 августа 2026
года (260 записей часов, 36 событий, 5 речей, 28 сессий). Импорт отвергал
файл целиком с сообщением **«Файл содержит повреждённые записи и не может
быть импортирован»** — без указания сущности, поля и причины.

Проверка реального файла показала следующее.

- Гипотеза «виновата речь `t6` с `number: null`» **не подтвердилась**:
  `validateTalk()` в TASK_013 явно разрешал `null`
  (`if (x.number !== null && !isFiniteNumber(x.number)) return false`).
- Настоящая причина — **семь событий**, у которых `category` содержит id
  пользовательской темы из TASK_045 (`x1784653775553td1`,
  `x1785309284359008`, `x1786957481658tlu`). В TASK_045 тип
  `MinistryEvent.category` был расширен с закрытого union из шести
  системных категорий до `string`, но валидатор бэкапа остался на
  `CATEGORY_KEYS.includes(x.category)` и вместе с ним расширен не был.
- Сопутствующий изъян: сами пользовательские темы
  (`mj_custom_categories_v1`) и профиль (`mj_profile_v1`) в копию вообще не
  попадали. Даже успешное восстановление на другом устройстве оставило бы
  эти семь событий без названия темы.

Общая ошибка без имени сущности и поля — то, из-за чего причину искали не
там. Поэтому задача не сводится к «разрешить `null`»: она про то, чтобы
проверка **называла** проблему.

## 2. Формат резервной копии v2

Расширение — **`.mfb`** (Ministry Backup File). Не `.afb`: это расширение
принадлежит Alex Finance. Содержимое остаётся JSON.

```typescript
type MinistryBackup = {
  format:     "ministry-backup";
  version:    2;
  appVersion: string;      // "0.4.4"
  createdAt:  string;      // ISO-8601
  counts: {
    records: number; events: number; talks: number;
    sessions: number; customCategories: number;
  };
  data: {
    records:  HourRecord[];
    events:   MinistryEvent[];
    talks:    Talk[];
    sessions: Session[];
    customCategories?: CustomCategory[];  // TASK_045 — только v2
    profile?:          UserProfile;       // TASK_042 — только v2
  };
  checksum: string;        // SHA-256, hex, нижний регистр
};
```

**Checksum.** `sha256(canonicalJSON(копия без поля checksum))`. Поле
`checksum` в расчёт не входит — иначе его нельзя было бы вычислить.
Канонизация (`src/data/sha256.ts`) сортирует ключи объектов и убирает
незначащие пробелы, поэтому сумма не зависит от форматирования файла:
pretty-printed экспорт и компактный `.mfb` с одинаковыми данными дают
одинаковую сумму, и переоткрытие файла в редакторе с перестановкой ключей
её не ломает.

SHA-256 реализован вручную (`src/data/sha256.ts`, ~60 строк) вместо
`crypto.subtle`: тот асинхронен и доступен не во всех точках матрицы
web/Jest/native, а из-за него весь путь построения и проверки копии стал
бы асинхронным. Новых зависимостей не добавлено. Это **проверка
целостности, а не защита**: сумма без ключа, и тот, кто правит файл, может
её пересчитать. Ровно эта гарантия и требуется.

Имена файлов:

| Действие | Имя | MIME |
|----------|-----|------|
| Экспорт данных | `ministry-export-YYYY-MM-DD-HHmm.json` | `application/json` |
| Резервная копия | `ministry-backup-YYYY-MM-DD-HHmm.mfb` | `application/octet-stream` |

Оба файла содержат **одинаковую полезную нагрузку v2** с контрольной
суммой; различаются только имя, расширение и форматирование. Экспорт —
читаемый (отступы), копия — компактная. Любой из них можно восстановить.
`application/octet-stream` для `.mfb` нужен, чтобы Safari/iOS не дописал
к имени `.json`, выведя тип из MIME.

## 3. Обратная совместимость с v1

Копии TASK_013 (`.json`, `version: 1`, четыре коллекции, без checksum)
по-прежнему открываются и восстанавливаются.

- Отсутствие checksum у v1 **не считается повреждением** — это ожидаемо, и
  предпросмотр говорит об этом прямо.
- Данные мигрируются в актуальную внутреннюю модель без правки JSON
  руками.
- Ни одна запись, событие, речь или сессия не теряются.
- Тем событий и профиля в v1 нет, поэтому восстановление **не трогает**
  соответствующие ключи на устройстве, а не затирает их пустыми
  значениями. Предпросмотр сообщает об этом отдельной строкой.
- Мигрированной копии заново вычисляется собственная контрольная сумма —
  того, что реально будет записано.

## 4. Проверка, предпросмотр и правила валидации

### 4.1 Порядок проверок

1. Размер файла (≤ 25 МБ).
2. `JSON.parse` → «Файл не удалось прочитать: неверный JSON.»
3. `format === "ministry-backup"` → «Это не резервная копия Ministry.»
4. `version` — целое ≥ 1; больше поддерживаемого → «создана более новой
   версией приложения».
5. `createdAt` — строгий ISO-8601.
6. **Checksum (только v2)** — до разбора содержимого, чтобы подделанный
   файл назывался подделанным, а не «сломанной записью»:
   «Контрольная сумма не совпадает: файл мог быть изменён или повреждён.»
7. Поэлементная проверка коллекций.

### 4.2 Критичные ошибки (восстановление невозможно)

Отсутствие `id`; отсутствие или неверный формат обязательной даты;
недопустимые `year`/`month`/`hours`/`durationMinutes`/`source`;
сессия таймера без `startTime`/`endTime`; отсутствие
`createdAt`/`updatedAt` у сессии; пустая или нетекстовая тема события;
пустое название темы; дубликат `id` внутри коллекции; текстовое поле
неверного типа; поле `number` речи не число и не пустое значение.

Каждая ошибка называет **сущность, номер, id, поле и причину**:

> Не удалось восстановить: у записи речи №1 (id: t6) отсутствует
> обязательная дата.

При нескольких проблемах заголовок дополняется «Всего проблем: N», а под
ним перечисляются первые шесть. Общая формулировка «файл содержит
повреждённые записи» **удалена из кода**; на её отсутствие есть тест.

Ни одна плохая запись не удаляется молча ради того, чтобы восстановление
прошло: либо копия восстанавливается целиком, либо не восстанавливается
ничего.

### 4.3 Совместимые данные и необязательные поля (принимаются)

| Случай | Поведение |
|--------|-----------|
| `talk.number: null` | Принимается как есть — это нормальное «без номера» |
| `talk.number` отсутствует | Нормализуется в `null`, отмечается в примечаниях |
| `talk.number: "75"` | **Ошибка** — угадывать намерение владельца нельзя |
| `record.creditHours` (TASK_039) | Сохраняется дословно; отсутствие = «нет зачёта» |
| `event.category` = id пользовательской темы | Принимается (исправление §1) |
| Отсутствующий `note`/`title`/`location` | Нормализуется в `""` — это внутреннее представление «не заполнено» |
| Неизвестные лишние поля | Сохраняются: элемент копируется целиком, а не пересобирается |
| Отсутствующие `customCategories`/`profile` | Признак v1; ключи на устройстве не трогаются |

Все нормализации подсчитываются и показываются в предпросмотре
(«Пустых необязательных полей приведено к текущему формату: N. Данные при
этом не менялись.»).

### 4.4 Предпросмотр

После выбора файла данные **не заменяются**. Открывается лист
«Восстановление из копии»:

- статус — зелёное «Копия готова к восстановлению» либо красная конкретная
  ошибка (с перечнем проблем и строкой «Текущие данные не изменены.»);
- «Создана» — дата и время;
- «Формат» — «Версия 2 (.mfb)» либо «Версия 1 (старая, совместимая)»;
- «Приложение» — версия приложения из копии;
- «Контрольная сумма» — «Проверена» либо «Нет (у версии 1 её и не бывает)»;
- таблица «Категория / Сейчас / В копии» по записям часов, сессиям,
  событиям и речам (плюс темы событий, если копия их содержит);
- примечания миграции;
- предупреждение «Все текущие данные Ministry на этом устройстве будут
  заменены данными из копии.»;
- кнопки «Отмена» и красная «Восстановить». При ошибке — только «Закрыть»,
  кнопки восстановления нет вовсе.

Значения полей попадают в текст ошибки только для структурных полей — дат,
чисел, перечислений, id. Никогда для `note`/`title`/`location`: там слова
владельца (правило приватности TASK_013 §7).

## 5. Безопасное восстановление

`performImport()` (`src/data/backupImport.ts`):

1. Снимок текущих значений всех поддерживаемых ключей (источник отката).
2. **Страховочная копия** текущих данных в `mj_backup_safety_v1`. Если её
   не удалось записать — восстановление не начинается вовсе.
3. Запись данных копии через штатные ключи приложения; пишутся только те
   коллекции, которые копия реально содержит.
4. Контрольное чтение: побайтовое сравнение **и** сверка фактических
   счётчиков сущностей с `counts` из копии.
5. `replaceAllData()` — применение к живому `StoreContext` последним шагом
   той же транзакции (исправление продакшн-бага TASK_013 §12).
6. Успех показывается только после пунктов 4–5.
7. При любой ошибке — откат снимка; текущие данные остаются прежними.
   Если и откат не удался, сообщение об этом честно говорит и не
   утверждает, что прежние данные на месте.

Как и в TASK_013, это application-level snapshot-and-rollback, а не
физическая атомарность `AsyncStorage.multiSet` — формулировка в шапке
файла сохранена без преувеличения гарантий.

`mj_timer_v1` и любые другие ключи не затрагиваются (тест на месте).

## 6. Экран «Данные и резервные копии»

Стиль Ministry сохранён (`ProfileSettingsRow` на токенах `DS`), экран Alex
Finance не копировался. Три строки вместо прежних двух:

| Строка | Иконка | Действие |
|--------|--------|----------|
| Экспорт данных | `DownloadIcon` | Читаемый `.json` со всеми данными |
| Создать резервную копию | `ShieldIcon` | Полный `.mfb` с контрольной суммой |
| Восстановить из копии | `RotateCcwIcon`, `tone="danger"` | Предпросмотр → подтверждение → замена |

Под ними — строка «Последняя копия: ДД-ММ-ГГГГ ЧЧ:ММ» либо «Резервная копия
ещё не создавалась». Значение хранится локально в `mj_last_backup_v1` и
обновляется только созданием файла копии; восстановление его не меняет.

Блок «Синхронизация — скоро через A-Lex Core» не тронут.

| Ключ | Содержимое | В копию? |

`StoreProvider` их не читает, восстановление их не перезаписывает.
Схема существующих ключей не менялась, миграций хранилища нет.

## 8. Объём (Scope)

**Входит:** формат v2 с контрольной суммой, `.mfb`, чтение и миграция v1,
поэлементная валидация с конкретными сообщениями, предпросмотр,
страховочная копия, атомарное восстановление со сверкой счётчиков,
перенос тем событий и профиля, три действия на экране «Данные и резервные
копии», отметка последней копии, тесты, документация.

**Не входит:** облачная синхронизация (блок A-Lex Core не тронут),
аккаунты, шифрование копий, финансовые функции Alex Finance (PDF, Excel,
CSV-экспорт операций, импорт банковских CSV), merge/разрешение конфликтов,
bump версии приложения, тег, деплой.
