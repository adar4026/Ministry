#### TASK_012 (доп.) — iOS Home Screen: фикс apple-touch-icon — задеплоен и проверен в проде

- **Проблема:** новая favicon видна в шэринг-шите Safari, но при «Добавить
  на экран Домой» iOS показывала дефолтную серую «G»-иконку — признак
  отсутствия валидного `apple-touch-icon`.
- **Причина:** Expo CLI автоматически инжектирует `<link rel="icon">` из
  `web.favicon`, но не имеет аналогичного механизма для
  `apple-touch-icon`. Проект использует `web.output: "static"`
  (SSG через expo-router), поэтому HTML-документ каждой статической
  страницы генерируется через корневой компонент `app/+html.tsx`
  (static rendering), а не через `public/index.html` template
  (последний — только для нестатического dev/SPA-режима и в
  продакшен-сборке не используется; первая попытка добавить тег через
  `public/index.html` была проверена и отклонена — тег не появлялся в
  экспортированном `dist/index.html`).
- **Исправление:** `public/apple-touch-icon.png` (180×180, PNG,
  непрозрачный, без белой рамки/отступов, получен из того же
  corner-filled артворка Ministry, что и `assets/icon.png` из основной
  части TASK_012) + `app/+html.tsx` (сгенерирован через `npx expo
  customize app/+html.tsx`, добавлен `<link rel="apple-touch-icon"
  href="/Ministry/apple-touch-icon.png" />`). `app.json`, favicon,
  Android adaptive-icon ассеты, версия, сплэш — без изменений.
- Проверки: `tsc --noEmit` — чисто; `jest` — 14 наборов / 159 тестов;
  `expo export --platform web` — тег `apple-touch-icon` подтверждён во
  всех 23 экспортированных статических HTML (включая `/`), путь
  использует базовый `/Ministry/` корректно; `favicon.ico` и его
  `<link rel="icon">` — без изменений.
- **Релиз:** коммит `a759f0b`
  (`fix(web): add apple-touch-icon for iOS Home Screen (TASK_012
  follow-up)`), запушен в `origin/main`; локальный HEAD == `origin/main`.
  Деплой — `npm run deploy`, gh-pages `b0d5383`.
- **Прод-проверка:** `https://adar4026.github.io/Ministry/apple-touch-icon.png`

- Ручной ввод минут текстом убран из `SessionForm.tsx` — длительность
  теперь выбирается двумя независимыми колёсами. Отправка/канцел
  вынесены из `SessionForm` в шапку экрана через `onStateChange`
  (`{canSubmit, submit}`), т.к. по референсу шапка не должна прокручиваться
  вместе с карточками.
- **Обнаруженное архитектурное расхождение (задокументировано, не
  блокирует):** референс-скриншот показывал вторую пилюлю «время суток»
  рядом с датой; `Session` для `source: "manual"` архитектурно не имеет
  `startTime`/`endTime` (TASK_005_ARCHITECTURE.md §6) — карточка «Дата»
  реализована без контроля времени суток, схема хранения не менялась. См.
  `docs/TASKS/TASK_011_HOURS_ENTRY_WHEEL_REDESIGN.md` §3.
- **Легаси-значения минут не кратные 5 (финальное, владельцем одобренное
  решение):** колесо минут содержит **только** стандартные значения
  `0, 5, 10, …, 55` — никаких произвольных пунктов (47, 22, 38 и т. п.)
  ни при каких обстоятельствах, ни для новых, ни для отредактированных
  легаси-записей. Промежуточное решение (инжекция точного легаси-остатка
  как дополнительного пункта колеса) было реализовано после первого
  ревью, но **явно отклонено владельцем** — колесо обязано оставаться
  строго 5-минутным. Вместо этого: длительность, чей остаток не кратен 5
  (легаси/таймер: `ceil(bankedSeconds/60)`), **округляется** к ближайшему
  кратному 5 функцией `roundDurationToNearestFive()`
  (`src/data/constants.ts`) один раз при монтировании экрана
  редактирования — стандартное округление (остаток 0–2 вниз, 3–4 вверх) с
  корректным переносом через час (58 → 60 → «1 час 0 минут»). Под
  карточкой «Время» показывается краткое информационное сообщение «Время
  округлено до ближайших 5 минут», если исходное значение не было кратно
  5. Авторитетное `durationMinutes` всегда честно вычисляется как
  `hours*60+minutes` из видимых значений колёс — отдельного скрытого
  «точного» состояния нет ни в одной из версий. Часы клампятся до 24
  (максимум колеса) для нереалистично длинных нормализованных
  длительностей — защитный клампинг, без изменения схемы хранения.
- Исправлен реальный веб-баг при верификации: `contentOffset` не сеет
  начальную позицию скролла на web (react-native-web применяет атомарные
  CSS-классы контента на тик позже первого рендера) — заменено на

### Архитектура и модель данных

- Expo + React Native (expo-router, TypeScript), Expo SDK 54.
- Единый `StoreContext` — вся работа с данными идёт только через него.
- **Session-first агрегация (TASK_005A, канонизирована в TASK_008):** для
  каждого месяца авторитетный источник ровно один — по **наличию**
  `Session` за месяц (не по знаку суммы), иначе легаси `HourRecord`.
  Источники никогда не смешиваются. `monthTotal()` и `sessionsForMonth()`
  живут в `src/data/stats.ts` (единственная реализация, приватный helper
  `resolveMonthTotal()`) и переэкспортируются без изменения сигнатур из
  `src/data/constants.ts`, откуда их импортируют все остальные модули;
  `serviceYearAggregation()` остаётся в `constants.ts`.
- **Статистика (TASK_005E):** чистые функции в `src/data/stats.ts`;
  компоненты в `src/components/stats/` (MonthlyStatsCard,
  ServiceYearStatsCard, TrendChart, PaceCard, ProjectionCard) +
  `src/components/HeatMap.tsx`. Hours Dashboard (`app/(tabs)/hours/index.tsx`)
  и HeatMap больше не агрегируют `records`/`sessions` напрямую (TASK_008) —
  оба потребляют `monthCellsForSY()`; HeatMap разрешает каждую ячейку по её
  собственной дате `YYYY-MM`, а не по одному общему году сентябрьской ячейки.
- **Правило блокировки легаси-записи (TASK_005B):** единая точка
  проверки — `legacyEntryBlockReason()` в `src/data/constants.ts`;
  легаси-форма отказывает для текущего/будущих месяцев и прошлых месяцев
  с сессиями, с явным пояснением в форме.
- **Таймер (TASK_005C):** `TimerState` — управляющее состояние
  (crash-recovery), не отчётная сущность; ключ `mj_timer_v1`; логика —
  `src/data/timer.ts`, жизненный цикл — `src/hooks/useTimer.ts`.
