## TASK_047 (предыдущее обновление)

Реализация завершена и закоммичена локально, push/deploy ожидают
разрешения владельца.

Владелец запросил доработку wheel picker на «Добавить время» в терминах
raw CSS (`scroll-snap-type`, `scrollend`) и Telegram Mini App haptics —
ни то, ни другое не относится к этому проекту (Expo/RN, не Telegram Mini
App; подтверждено `grep -rli telegram` — ноль совпадений). Владелец
подтвердил: не переписывать компонент, а закрыть реальные пробелы в уже
существующем `src/components/WheelPicker.tsx` (TASK_011, физически
откалиброван в TASK_030) относительно каждого запрошенного сценария.

Найдено и исправлено два реальных бага, оба подтверждены живьём на
dev-сервере (`localhost:8082/entry`) до и после исправления:

1. **На web `onScrollEndDrag`/`onMomentumScrollEnd` никогда не
   срабатывают** — прочитан исходник `react-native-web`
   (`ScrollViewBase.js`): эти пропсы принимаются, но не вызываются
   внутри компонента; на web `WheelPicker.handleScrollEnd`
   (→ `snapToIndex`) никогда не запускался сам по себе. Строка визуально
   центрировалась (`opacity` от отдельного `onScroll`), но значение не
   фиксировалось — «Добавить» оставалась неактивной. Исправление:
   web-only debounce 130мс в `onScroll`, сбрасываемый на каждый тик,
   вызывающий тот же `handleScrollEnd`. Native не затронут — там реальные
   события от платформы приходят раньше.
2. **`onChange`-дедупликация зависела от пропа `value`, не от ref** —
   при гонке «реальный settle + web-debounce на тот же индекс» мог
   сработать дважды, если React ещё не прокинул новый `value` обратно.
   Теперь `onChange` в одном `if` с haptic-логикой, которая уже
   использовала ref (`lastHapticIndex`) — гарантированно один раз,
   независимо от таймингов рендера.

Не менялось: `StoreContext`, `SessionForm.tsx`, `entry.tsx`,
`DurationWheelPicker.tsx`, `ITEM_HEIGHT` (30, ранее откалиброван на
устройстве в TASK_030), ключи AsyncStorage, диапазоны часов/минут,
визуальный дизайн — единственный изменённый файл реализации —
`src/components/WheelPicker.tsx`.

### TASK_013 — Резервная копия данных: экспорт/импорт (Safari → PWA) — задеплоена, проверена в проде (UI), физическая проверка на iPhone ожидается

#### TASK_013 (iOS PWA picker-фикс) — отложенный `change` терялся из-за 300мс focus-отмены — задеплоен, проверен в проде (read-only)

- **Проблема (обнаружена владельцем на реальном iPhone):** валидный

- **Причина:** `pickBackupFile()` в `src/data/backupFile.web.ts`
  возвращал одноразовый `Promise`, застрахованный 300мс таймером-
  фолбэком на `window.focus` (введён ранее как защита от Safari-версий,
  не эмитящих `cancel`). На iOS PWA фокус окна может вернуться из Files
  раньше, чем браузер успевает диспатчить `change` у `<input
  type=file>`. Таймер отклонял Promise как `cancelled`, а
  `cleanup()` в этот же момент снимал все слушатели и удалял `<input>`
  из DOM — пришедшее позже настоящее событие `change` попадало на уже
  отсоединённый, безслушательный узел и терялось без следа (без ошибки,
  так как `BackupSection` трактовал `cancelled` как молчаливую отмену).
- **Исправление:** `src/data/backupFile.web.ts` — пикер переведён с
  одноразового Promise на постоянный (module-owned singleton, создаётся
  лениво один раз и живёт весь срок жизни страницы) скрытый `<input>` с
  callback-API (`onSelected`/`onError`/`onCancelled`) вместо
  `Promise<string>`. Фокус-эвристика и явное событие `cancel` теперь
  лишь неразрушающе сигнализируют UI («можно снять индикатор
  загрузки») через `onCancelled` — они никогда не отклоняют, не

  того как `onCancelled` уже сработал. `input.value` сбрасывается сразу
  после каждой обработки — тот же файл можно выбрать повторно.

- **Легаси-значения минут не кратные 5 (финальное, владельцем одобренное
  решение):** колесо минут содержит **только** стандартные значения
  `0, 5, 10, …, 55` — никаких произвольных пунктов (47, 22, 38 и т. п.)

  легаси-записей. Промежуточное решение (инжекция точного легаси-остатка
  как дополнительного пункта колеса) было реализовано после первого
  ревью, но **явно отклонено владельцем** — колесо обязано оставаться
  строго 5-минутным. Вместо этого: длительность, чей остаток не кратен 5

  редактирования — стандартное округление (остаток 0–2 вниз, 3–4 вверх) с
  корректным переносом через час (58 → 60 → «1 час 0 минут»). Под

### Архитектура и модель данных

- Expo + React Native (expo-router, TypeScript), Expo SDK 54.
- Единый `StoreContext` — вся работа с данными идёт только через него.
- **Session-first агрегация (TASK_005A, канонизирована в TASK_008):** для
  каждого месяца авторитетный источник ровно один — по **наличию**
  `Session` за месяц (не по знаку суммы), иначе легаси `HourRecord`.
  Источники никогда не смешиваются. `monthTotal()` и `sessionsForMonth()`
  живут в `src/data/stats.ts` (единственная реализация, приватный helper
  `resolveMonthTotal()`) и переэкспортируются без изменения сигнатур из
  `src/data/constants.ts`, откуда их импортируют все остальные модули;
  `serviceYearAggregation()` остаётся в `constants.ts`.
- **Статистика (TASK_005E):** чистые функции в `src/data/stats.ts`;
  компоненты в `src/components/stats/` (MonthlyStatsCard,
  ServiceYearStatsCard, TrendChart, PaceCard, ProjectionCard) +
  `src/components/HeatMap.tsx`. Hours Dashboard (`app/(tabs)/hours/index.tsx`)
  и HeatMap больше не агрегируют `records`/`sessions` напрямую (TASK_008) —
  оба потребляют `monthCellsForSY()`; HeatMap разрешает каждую ячейку по её
  собственной дате `YYYY-MM`, а не по одному общему году сентябрьской ячейки.
- **Правило блокировки легаси-записи (TASK_005B):** единая точка
  проверки — `legacyEntryBlockReason()` в `src/data/constants.ts`;
  легаси-форма отказывает для текущего/будущих месяцев и прошлых месяцев
  с сессиями, с явным пояснением в форме.
- **Таймер (TASK_005C):** `TimerState` — управляющее состояние
  (crash-recovery), не отчётная сущность; ключ `mj_timer_v1`; логика —

## Данные

Историческая информация пользователя (записи часов, события, публичные
речи) не воспроизводится в публичной документации проекта — ни числовыми
таблицами, ни отдельными записями, ни датами, ни примечаниями. Начиная с
TASK_009:

- реальные данные пользователя авторитетно хранятся локально на устройстве,
  в AsyncStorage (см. «Хранилище (AsyncStorage)» выше) — это единственный
  источник истины после первого запуска;
- верифицированная приватная резервная копия существует **вне
  репозитория**; её путь и контрольная сумма намеренно не публикуются в
  этом документе;
- публичные seed/source-файлы (`src/data/seed.js`) содержат только пустые
  массивы для первого запуска и не восстанавливаются из приватной резервной
  копии в публичное дерево исходников (TASK_009).
